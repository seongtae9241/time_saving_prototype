## 1. 개요와 읽는 법

- 이 문서는 "무엇을 만들었고 무엇이 남았는지"를 기능 단위로 적는다. 왜 필요한지와 규칙은 요구사항 정의서에 있다.
- **2절 기능 목록**에서 전체를 한 줄씩 보고, **3절 기능별 상세**에서 우선순위 상·AI 기능·기관 담당자 기능 전부를 자세히 본다. 나머지는 2절의 한 줄 설명이 전부다.
- **대표가 맡는 기관 담당자 구역은 3.3절**에 모았다. "지금 있는 것"과 "PC 화면 명세서에만 있고 아직 없는 것"을 나눴다.

### 1.1 기능 ID 체계

| 접두 | 구분 | 원래 번호 | 더한 번호 |
|---|---|---|---|
| `C-` | 공통 | C-01~C-08 | C-09+~C-14+ |
| `U-` | 사용자 | U-01~U-35 | U-36+~U-49+ |
| `O-` | 기관 담당자 | O-01~O-13 | O-14+~O-42+ |
| `A-` | 운영자 | A-01~A-17 | A-18+~A-31+ |

- 원래 번호는 `docs/requirements/기능명세서.txt`(73개)의 ID를 그대로 쓴다.
- **`+`가 붙은 번호**는 기능명세서에 없지만 41판 요구사항, 계약서 추가 절, 11/13 대표 지시, PC 화면 명세서에서 온 기능이다. 이어지는 번호를 붙였다.
- 41판 요구사항 ID(A-/B-/C-/D-)와 글자가 겹치므로, 이 문서에서 ID만 적은 것은 모두 **기능 ID**다. PC 화면 명세서의 화면 ID(O-HOME-01, A-06 등)는 "화면 O-HOME-01"처럼 적는다.

### 1.2 표기

| 표기 | 뜻 |
|---|---|
| ✨ | AI(LLM)를 쓰는 기능. 키가 없으면 규칙 문장으로 대신한다 |
| 우선순위 | 상 = 발표 시연에 꼭 필요 / 중 = 있으면 좋음 / 하 = 시간 남으면. `*`는 기능명세서에 없어 문서 담당이 판단한 값 |
| 구현됨 | 기준 커밋의 코드에 동작이 있다 |
| 일부 | 일부만 있거나 명세와 다르거나 미커밋 작업 중 |
| 미구현 | 정해졌지만 코드가 없다 |
| 미정 | 회의·대표 결정이 먼저 필요하다 |
| 화면 | 지금 코드의 경로(`/o/home`). 괄호 안은 PC 화면 명세서의 화면 ID |

## 3. 기능별 상세

우선순위 상, AI(✨) 기능, 기관 담당자 기능 전부를 적었다. 공통·사용자·운영자는 짧은 틀로, 기관 담당자는 긴 틀로 썼다. API는 경로만 적었다(모두 `/api` 아래, 자세한 본문은 `docs/design/contract.md`).

### 3.1 공통

**C-01 회원가입** (상)
- 목적·사용자: 새 사용자가 계정을 만든다.
- 흐름: ① 휴대폰 번호로 인증번호 받기 ② 번호 확인 ③ 이름·동네·나이대·아이디·비밀번호 ④ 약관 동의(필수 2·선택 2) ⑤ 가입과 함께 로그인, 통장 번호 부여.
- 예외: 필수 약관이 빠지면 가입 안 됨. 아이디 중복이면 거절.
- 규칙: BR-037. API: `/auth/phone/send`, `/auth/phone/verify`, `/auth/signup`.
- 남은 것: 본인인증이 데모 번호(모의). 실제 문자는 Firebase 키가 필요하다.

**C-02 로그인·로그아웃** (상)
- 흐름: 아이디·비밀번호 → 토큰 발급(로그인 유지 30일, 아니면 1일) → 역할에 맞는 홈으로.
- 예외: 정지·퇴출·탈퇴 계정은 로그인 안 됨. API: `/auth/login`, `/auth/logout`, `/me`.

**C-03 기관 서비스 신청** (상)
- 목적·사용자: 주민센터·복지관 담당자가 서비스 이용을 신청한다(로그인 전).
- 흐름: ① 기관명·종류·주소·전화 ② 담당자 이름·연락처 ③ 재직 증빙 파일 ④ 제출 → 운영자 승인 대기 ⑤ 승인되면 운영자가 첫 담당자 계정과 임시 비밀번호를 발급(A-10).
- 예외: 증빙·주소가 없으면 접수 안 됨. 같은 IP 10분에 5번까지.
- API: `/orgs/apply`. 남은 것: 없음.

**C-05 알림 목록** (상)
- 흐름: 알림을 최근 순으로 본다 → 누르면 읽음 처리와 함께 관련 화면으로 → "모두 읽음".
- 규칙: 관리 대상 건의 알림은 담당자에게 간다(BR-032). 꺼 둔 종류는 만들어지지 않는다.
- API: `/notifications`, `/notifications/{id}/read`, `/notifications/read-all`, `/notifications/unread-count`.

**C-12+ 요청·제안 메시지** (상*)
- 흐름: 상대가 수락한 뒤 요청 상세에서 글을 보낸다 → 상대에게 알림 → 활동이 끝나면 읽기만.
- 예외: 연락처·계좌로 보이는 글은 경고 표시가 붙는다(막지는 않음). 메시지마다 신고할 수 있다.
- 규칙: BR-029. API: `/requests/{id}/messages`, `/requests/{id}/message-assist`.

### 3.2 사용자

**U-01 모드 토글** (상)
- 흐름: 헤더에서 도움 받기/봉사하기를 고른다 → 홈·공고 목록·플래너·활동 내역이 그 역할 것으로 바뀐다.
- 서버 계약은 플래너 주 보기(`mode`)뿐이고 나머지는 화면이 거른다.

**U-02 공고 목록** (상)
- 흐름: 모드에 맞는 공고 목록 → 지역·카테고리·날짜 필터 → 정렬(가까운 순·최신순·시간순) → 카드를 눌러 상세.
- 예외: 위치 동의가 없으면 가까운 순 대신 시간순.
- API: `/posts`, `/posts/bookmarks`. 11/13 지시의 탭 3종(1:1 / 단체 / 동네 기관 소식)과 관심 공고 구역 먼저는 `9f78dc4`에서 반영(U-48+).

**U-03 공고 상세** (상)
- 출력 순서: 시간 → 필요한 도움 → 내용 → 담당자(관리 대상 공고만: 기관·이름, 연락처 없음) → 특이사항 및 요청사항(요청자 한마디 / 담당자 특이사항). 작성자 신뢰 배지·평점, 예상 적립 시간.
- 규칙: 담당자 특이사항은 확정된 봉사자에게만(BR-031). 확정 전에는 "확정되면 보여요" 잠금 안내.
- API: `/posts/{id}`.

**U-04 AI 공고 작성 ✨** (상)
- 목적·사용자: 글쓰기가 어려운 사용자·담당자가 말하듯 적어 공고를 만든다.
- 흐름: ① "새로운 사람 / 단골"을 고른다 ② 필요한 도움을 적는다 ③ AI가 모자란 칸(날짜·시간 범위·장소·내용)을 되묻는다 ④ 정리된 공고 요약을 본다 ⑤ 고치고 버튼을 눌러 등록.
- 예외: 불가 요청이면 등록이 막히고 이유와 "근처 공공 서비스 찾기"가 나온다. "매주"라고 하면 정기 요청 안내로 넘어간다.
- AI가 하는 일: 대화로 되묻기, 칸 채우기. 코드가 하는 일: 금지 요청 판정, 날짜·시간 규칙 검사, 난이도 가중치.
- 규칙: BR-008, BR-023. API: `/ai/post-chat`, `/ai/filter`, `/ai/difficulty`, `/posts`.
- 남은 것: 실제 AI로 확인 안 됨.

**U-05 직접 공고 작성** (상)
- 흐름: 공고 종류를 고른다 → 날짜·시간 범위·지역·카테고리·내용을 채운다 → 예상 적립을 확인 → 등록. 수락 전에는 수정·삭제 가능.
- 예외: 봉사 가능 공고는 봉사 자격(BR-027)이 있어야 한다. 도움 요청은 10시간 조건(BR-005)과 잔액을 본다.
- API: `/posts`, `/posts/{id}`, `/posts/mine`.

**U-12 빈 시간 묶음 추천 ✨** (상)
- 목적·사용자: 봉사하는 사용자가 하루의 빈 시간에 여러 건을 이어서 한다.
- 흐름: ① 날짜와 가능한 시간 범위(1시간 30분 이상)를 넣는다 ② 묶음 최대 3개(각 2~3건)를 이동 거리·대기 시간·예상 적립과 함께 본다 ③ 묶음을 골라 "한 번에 제안".
- 예외: 일부 공고만 실패하면 건마다 성공·실패를 알려 준다.
- AI: 묶음 설명 한두 문장. 코드: 후보 고르기, 거리, 간격(걷는 시간 + 10분, 최소 30분), 순위.
- API: `/bundles/recommend`, `/bundles/propose`. 남은 것: 이동 시간이 직선거리·가상 좌표.

**U-13 요청·제안 보내기** (상)
- 흐름: 공고 범위 안에서 시작 시각·활동 시간(30분 단위, 최대 4시간)·도움 내용·메모를 정해 보낸다 → 상대가 24시간 안에 응답.
- 예외: 10시간 조건·잔액 부족이면 요청 불가. 제안은 봉사 자격이 필요. 공고 범위를 벗어나면 거절.
- 규칙: BR-005, BR-008, BR-009. API: `/requests`.

**U-14 진행 화면** (상) · **U-40+ 수락·거절·최종 수락** (상*)
- 흐름: 단계 바(요청 → 수락 → 확정 → 진행 → 일지 → 완료)와 지금 할 일 버튼을 본다. 봉사자 수락 → 받는 사람 최종 수락(확정, 받는 쪽 시간 보류) → QR 시작·종료 → 일지 → 확인 → 평가.
- 예외: 거절은 사유를 고른다. 하나가 확정되면 같은 공고의 나머지는 자동 거절. 응답 전 취소는 보낸 쪽만.
- 규칙: BR-010~BR-012, BR-017. API: `/requests/{id}`, `/requests/{id}/accept`, `/reject`, `/confirm`, `/decline`, `/cancel`.

**U-15 QR 시작·종료** (상)
- 흐름: 받는 사람 화면에 QR과 6자리 번호(30초마다 바뀜) → 봉사자가 찍거나 번호 입력 → 시작 시각 기록 → 끝날 때 같은 방식으로 종료.
- 예외: 번호가 틀리거나 지나면 거절. 종료 기록이 없으면 예정 종료 30분 뒤 자동 마감. 예정과 30분 이상 다르면 양쪽 안내.
- 규칙: BR-015, BR-019. API: `/requests/{id}/qr`, `/check-in`, `/check-out`.

**U-17 봉사 일지 ✨** (상)
- 흐름: ① 한 줄 기록을 쓴다 ② "다듬기"를 누르면 읽기 쉬운 일지로 바뀐다 ③ 필요한 사진을 붙인다(U-16) ④ 제출 → 받는 사람(관리 대상이면 담당자)에게 전달 ⑤ 확인 또는 24시간 뒤 자동 확정 → 적립.
- AI: 한 줄 기록을 다듬기(없는 사실을 더하지 않음). 코드: 제출·확인·적립, QR 시각 넣기.
- 규칙: BR-003, BR-020~BR-022. API: `/ai/log-tidy`, `/requests/{id}/log`, `/requests/{id}/confirm`.

**U-21 잔고 · U-22 사용 내역** (상)
- 출력: 통장 번호, 쓸 수 있는 시간, 묶인 시간, 누적 번 시간·쓴 시간, 월별 합계, 건별 계산식(시간 × 난이도).
- 규칙: BR-012~BR-014. API: `/bank`.
- U-22: 월 넘기기, 건마다 ±시간·그 뒤 잔액·도운 분/도와준 분, 거래 상세까지 반영됨(`aeed99f`·`9f78dc4`). 선물·조정 거래는 상대 이름이 없다.

**U-24 시간 플랜 ✨** (상)
- 흐름: 나이와 도움 받기 시작 나이를 바꿔 본다 → 지금 속도로 모이는 시간, 받을 수 있는 기간, 90세까지 받는 데 필요한 한 달 적립 목표를 본다.
- AI: 설명 문장·적립 목표 문구. 코드: 비슷한 사람(같은 나이대 → 60대 이상) 평균, 적립 속도, 기간·목표 계산.
- API: `/me/time-plan`. 남은 것: 기록이 5명 미만이면 가정값(화면에 밝힘).

**U-30 공공 서비스 안내 AI ✨** (상)

**U-31 동네 기관 소식 ✨** (중) — 근처 기관 행사(담당자가 올린 것)와 공공 강좌 추천을 보여 준다. AI는 강좌 추천 이유·쉬운 요약. API `/events`, `/news`, `/public-classes/recommend`.

**U-35 봉사 확인서 ✨** (하) — 기간의 횟수·시간·주요 활동은 코드가 모으고, 자기소개용 요약 문장만 AI. PDF는 브라우저가 만든다. API `/certificate`.

**U-36+ 말로 요청하기 ✨** (중*) — 음성을 글로 바꿔(서버 음성 인식 또는 브라우저) U-04와 같은 흐름으로 간다. 위급한 말이면 119 안내, 개인정보로 보이는 말은 지운다. API `/stt`, `/ai/post-chat`.

**U-44+ 생애 플랜 ✨** (상*) — 모이는 시간·쓸 수 있는 기간은 코드가 계산하고 설명 문장만 AI(숫자는 바꾸지 못함). API `/me/life-plan`. 11/13의 꺾은선 그래프와 플래너 순서(생애 플랜 → 캘린더 → AI 추천)는 `9f78dc4`에서 반영.

### 3.3 기관 담당자 (전부)

> 지금 화면은 모바일 모양의 아래 탭 6칸(홈·도움 대상·편성표·요청 관리·리포트·마이)이다. PC 화면 명세서는 왼쪽 메뉴 9개의 PC 화면을 요구한다(O-42+). 아래 "화면"의 괄호는 PC 명세의 화면 ID다.

#### 가. 지금 구현된 것

**O-01 관리 대상 등록** (상) — `/o/elders/new` (O-CARE-03)
- 목적: 담당자가 챙길 어르신을 개인정보를 최소로 등록한다.
- 사용자: 승인된 기관의 담당자.
- 선행 조건: 담당자 계정으로 로그인. 대상에게 서비스 이용을 설명하고 동의를 받았다.
- 기본 흐름: ① 별칭 입력 ② 동("○○동") ③ 나이대(60대~90대 이상) ④ 필요한 도움(카테고리 여러 개) ⑤ 방문 주의사항 ⑥ "설명하고 동의를 받았음" 체크 ⑦ 저장 → 목록에 추가, 현관 QR 카드 번호 부여.
- 예외·대체: 동의 체크가 없으면 저장 안 됨. 전화번호·계좌·상세 주소가 보이면 거절(`PII_NOT_ALLOWED`). 수정 화면에서 같은 칸을 고치고, 동의 기록이 없는 옛 대상은 동의를 남길 수 있다.
- 입력·출력: 입력 = 위 칸. 출력 = 대상 정보 + 가린 이름("이○례 님") + 동의 여부.
- 업무 규칙: BR-030, NFR-001, NFR-003.
- 관련 API: `/org/elders`, `/org/elders/{id}`.
- 상태와 남은 것: 구현됨. PC 명세는 실명·정확한 나이·가구 형태·전화·주소·가족 연락처·위임을 함께 받는다(O-30+, O-31+, O-33+) — 원칙이 바뀌는 일이라 회의 결정이 먼저다.

**O-02 관리 대상 목록·상세** (상) — `/o/elders`, `/o/elders/:id` (O-CARE-01·02)
- 목적: 대상의 상태를 보고 대신 요청으로 이어 간다.
- 기본 흐름: ① 목록에서 별칭, 단골 수, 진행 중 건수, 이번 달 완료 횟수, "확인 권장" 칩을 본다 ② 대상을 누른다 ③ 상세에서 정보·주의사항, 단골 봉사자, 이번 달 활동, 받은 도움 기록, 담당자 메모를 본다 ④ 빠른 메뉴(공고 대신 등록, 봉사 공고에 요청, 단골에게 요청, 메모 쓰기, 지난 요청 다시 올리기, 정기 요청, 편성표, 통화 메모로 공고, QR 카드, 이관, 종료)로 간다.
- 예외: 다른 기관의 대상은 보이지 않는다(403).
- 업무 규칙: BR-024(단골), BR-032.
- 관련 API: `/org/elders`, `/org/elders/{id}`, `/org/care-signals`.
- 상태와 남은 것: 구현됨. 검색·필터 칩, 연락처 카드, 권한 위임 카드, "이번 주 돌봄" 5칸은 없다.

**O-03 대리 봉사 요청 ✨** (상) — `/write/need?elder=`, `/voice` (O-POST-02)
- 목적: 전화로 들은 부탁을 대상 대신 공고로 올린다.
- 선행 조건: 지원 중인 내 담당 대상.
- 기본 흐름: ① 대상을 고른다 ② 전화로 들은 내용을 적거나 말한다(예: "다음 주 화요일 정형외과 오후 2시 예약") ③ "AI로 공고 정리" ④ 카테고리(가중치)·날짜·시간·장소·내용이 채워진 공고를 본다 ⑤ 고친다 ⑥ 이슈 메모 칸에 주의사항이 미리 채워진 것을 확인·수정 ⑦ 올리기 → 요청 관리에 나타난다.
- 예외·대체: 금지 요청이면 등록이 막힌다. 날짜·시간이 모자라면 되묻는다. "매주"면 정기 요청으로 넘긴다(O-22+). 단골이 있으면 공고 없이 "바로 요청"(O-26+).
- 입력·출력: 입력 = 대상, 들은 내용. 출력 = 공고(대상의 가린 이름으로 표시).
- 업무 규칙: BR-007(무차감), BR-008, BR-023, BR-031.
- AI가 하는 일: 들은 내용을 공고 칸으로 정리. 코드가 하는 일: 날짜·시각 읽기, 금지 판정, 등록 검사, 주의사항을 이슈 칸으로 보내기.
- 관련 API: `/ai/tidy-post`, `/ai/post-chat`, `/posts`.
- 상태와 남은 것: 구현됨. 실제 AI로 확인 안 됨. PC 명세의 두 칸 화면(왼쪽 입력, 오른쪽 정리 결과)은 없다.

**O-04 이슈 메모** (상) — 작성 화면, `/post/:id`, `/o/reqs/:id` (O-POST-02·03)
- 목적: 봉사자가 알아야 할 대상 특이사항(귀가 어두움, 반려견 등)을 일정이 확정된 사람에게만 알린다.
- 기본 흐름: ① 담당자가 대리 공고의 이슈 메모 칸에 적는다(대상의 방문 주의사항이 미리 채워짐) ② 확정 전 봉사자에게는 잠금 안내만 보인다 ③ 최종 수락으로 확정되면 그 봉사자의 공고 상세·요청 상세·방문 전 브리핑에 보인다.
- 예외: 거절·취소·만료된 봉사자는 볼 수 없다. 300자까지.
- 업무 규칙: BR-031.
- 관련 API: `/posts`, `/posts/{id}`, `/requests/{id}`, `/requests/{id}/briefing`, `/recurring`.
- 상태와 남은 것: 구현됨. 정기 요청으로 넘길 때 공개 칸으로 새던 길은 고쳤다(`1f153ca` — 화면이 이슈 칸으로 보내고 서버도 옮긴다). 이 기능 전에 올린 공고의 공개 메모에 남은 "방문 시 주의: …" 글은 그대로다(이미 돌고 있는 DB에 한함).

**O-05 대신 수락·거절** (상) — `/o/reqs`, `/o/reqs/:id` (O-POST-01·03)
- 목적: 계정이 없는 대상에게 온 요청·제안을 담당자가 전화로 확인하고 처리한다.
- 기본 흐름: (제안이 온 경우) ① 알림·요청 관리에서 제안을 연다 ② 봉사자 카드(평점, 활동 수, 단골)를 본다 ③ 대신 수락(= 확정) 또는 사유를 골라 대신 거절. (대상 쪽에서 요청을 보낸 경우) ① 봉사자가 수락한다 ② 담당자가 대상에게 전화·방문으로 확인한다 ③ "전화로 일정을 확인했어요"를 체크한다 ④ 대신 최종 수락.
- 예외: 체크가 없으면 최종 수락 버튼이 눌리지 않는다. 24시간 안에 처리하지 않으면 만료된다.
- 업무 규칙: BR-009, BR-011, BR-032.
- 관련 API: `/org/requests`, `/requests/{id}/accept`, `/reject`, `/confirm`, `/decline`.
- 상태와 남은 것: 구현됨. PC 명세의 "홈 표에서 바로 수락·거절"은 없다(O-25+).

**O-06 도움 찾기** (중) — `/board?elder=` (O-POST-04)
- 기본 흐름: ① 대상을 고른다 ② 봉사 가능 공고를 지역·시간·카테고리로 찾는다 ③ 공고 범위 안에서 시간과 도움 내용을 정해 대신 요청 ④ 봉사자가 수락하면 O-05의 최종 수락으로.
- 업무 규칙: BR-008. 관련 API: `/posts`, `/requests`.
- 상태와 남은 것: 구현됨. PC 명세의 "카테고리 자동 선택, 단골·같은 동 먼저"는 확인 필요.

**O-07 단체 봉사 공고** (중) — `/group/new`, `/group/:id`, `/board?tab=group&kind=mine` (O-POST-05·08)
- 목적: 기관의 봉사거리에 여러 명을 모으거나, 봉사 단체의 제안을 기관이 받는다.
- 기본 흐름: (모집형) ① 날짜·시간·장소·카테고리·인원(2~50명)·내용으로 올린다 ② 사용자가 선착순으로 참여한다 ③ 활동 날부터 명단에서 참석자를 고른다 ④ 완료 → 참석자마다 시간(시간 × 1.0)이 적립되고 나머지는 불참 처리. (제공형) ① 봉사 단체가 올린 공고에서 "우리 기관에서 받기" ② 뒤는 같다.
- 예외: 활동 날 전에는 완료할 수 없다. 제공형은 한 기관만 받을 수 있다. 공고를 내리면 참여자에게 알림.
- 업무 규칙: BR-026, BR-023.
- 관련 API: `/group-posts`, `/group-posts/mine`, `/group-posts/{id}`, `/group-posts/{id}/host`, `/unhost`, `/complete`.
- 상태와 남은 것: 구현됨. 참석 확인은 명단 방식(PC 명세는 "당일 기관에서 QR"). 신청을 하나씩 수락·거절하는 단계는 없다(O-37+). 기관이 발행하는 시간의 재원은 회의 항목(M-05).

**O-08 일지 확인** (상) — `/o/reqs/:id`, `/req/:id/rate` (O-POST-03)

- 상태와 남은 것: 일부. PC 명세 O-HOME-01의 KPI 네 칸(관리 대상 / 이번 주 돌봄 / 처리할 일 / 편성 빈칸), 표 안에서 바로 `[대신 거절]` `[대신 수락]`, 편성 미리보기, 안부 Top 3, 새로 온 요청 3종(공공 서비스·기관 공고 신청·권한 위임), 최근 도착한 일지는 없다.

**O-26+ 단골에게 대신 요청** (중*) — `/regular?elder=` — 대상의 단골(별칭 기준, 완료 3회 이상 자동)에게 공고 없이 요청을 보낸다. 봉사자가 수락하면 O-05의 최종 수락으로. API `/regulars`, `/requests`. 구현됨.

**O-27+ 월간 생활 리포트 ✨** (하*) — `/o/report` — 대상별 월간 리포트를 보고 큰 변화에 표시하며 공유 동의를 대신 입력한다. 숫자는 코드, 서술만 AI. API `/org/reports`, `/org/reports/{id}/flag`, `/org/elders/{id}/consent`. 구현됨. 41판·기능명세서에 없는 옛 기능이라 남길지 확인 필요.

**O-28+ 공공 강좌 추천 ✨** (하*) — 대상에게 맞는 근처 공공 강좌를 보여 주고 "같이 가 주세요" 동행 공고 문장을 만들어 준다. API `/org/elders/{id}/public-classes`, `/public-classes/{id}`. 구현됨.

**O-29+ 담당자 마이·알림 설정** (하*) — `/o/my`, `/my/noti` — 알림 종류, 큰 글씨, 내 정보, 공지·문의·건의, 탈퇴, 이관 받은 요청. API `/me`, `/me/noti-settings`. 구현됨.

**O-30+ 실명·연락처·주소 저장** (상*, 미정) — (O-CARE-02·03)
- 목적: 담당자가 앱 안에서 바로 안부 전화를 걸고 주소를 확인한다.
- 기본 흐름(명세): ① 등록 패널에서 이름, 본인 전화번호, 도로명 주소 + 상세 주소(동·호수, 엘리베이터), 가족 연락처(관계·이름·전화, 여러 명)를 넣는다 ② 상세의 "연락처 · 안부 확인" 카드에 "담당자만 봐요"와 함께 보인다 ③ 봉사자에게는 이름을 가려 보여 주고 확정 뒤 방문 주소만 담당자가 알린다.
- 업무 규칙: 지금의 BR-030·NFR-001과 정반대다.
- 필요한 것: 대표·회의 결정(M-01: 개인정보 동의 문구, 보관 기간), 관리 대상 표에 칸 추가, 서버의 전화번호·주소 거절 규칙 바꾸기, 암호화와 열람 기록, 다른 기관·봉사자 응답에 섞이지 않게 하는 검사.

**O-31+ 가구 형태·앱 사용·검색 필터** (중*, 미구현) — (O-CARE-01·03)
- 기본 흐름(명세): 등록 때 정확한 나이, 가구 형태(혼자·배우자와·자녀와·기타), 앱 사용(앱 써요 / 전화만 받아요)을 받는다. 목록에서 이름·전화로 바로 거르고 칩(전체 / 동별 / 우선순위 높음 / 혼자 사는 분 / 앱 쓰는 분)으로 거른다. 행에 마지막 안부 확인일, `앱`·`우선` 배지.
- 필요한 것: 칸 추가, 앱 사용자와 관리 대상을 잇는 방식 결정(M-03), 우선순위는 O-10의 점수를 다시 쓸 수 있다.

**O-32+ 안부 확인 기록** (상*, 미구현) — (O-CARE-02, O-RPT-01)
- 기본 흐름(명세): ① `[📞 본인]` `[📞 가족]`으로 전화 ② `[안부 확인 기록]`을 누르면 오늘 날짜로 기록 ③ 목록과 리포트의 "마지막 안부 확인일"이 바뀐다. 리포트 목록의 `[안부 확인함]`도 같은 기록이다.
- 필요한 것: 안부 확인 기록 표와 API, 리포트 우선순위에 "최근 확인함"을 반영할지 결정. 전화 걸기는 O-30+가 먼저다(연락처 없이 기록만 먼저 만들 수는 있다).

**O-33+ 권한 위임 등록** (상*, 미구현) — (O-DLG-01·03, O-CARE-03)
- 목적: 담당자가 대신 하는 일의 범위·기간·동의를 분명히 한다.
- 기본 흐름(명세): ① 대상을 고른다 ② 동의 방법을 고른다 — 앱으로 동의 요청 / 서면 동의서(사진·PDF) 올리기 / 보호자 동의(가족 연락처로 동의 링크 문자) ③ 맡길 일을 고른다(대신 공고 / 대신 수락 / 일지 확인 / 공공 서비스 / 안부 확인, 1개 이상) ④ 기간(시작·끝, 최대 1년) ⑤ 등록 → 상태 "확인 대기" → 동의되면 "위임 중". 새 대상 등록 패널에서도 함께 받는다.
- 업무 규칙: BR-033(안).
- 필요한 것: 위임 표·API, 맡긴 일이 꺼져 있으면 O-03·O-05·O-08·O-15+를 막는 검사, 서면 동의서 양식(M-08), 문자 발송 업체, 지금 대상의 "동의 받았음" 기록을 어떻게 옮길지.

**O-34+ 위임 상세·변경·기록** (상*, 미구현) — (O-DLG-01·02)
- 기본 흐름(명세): ① 위임 목록에서 대상(앱 배지), 동의 방법, 맡긴 일 수, 기간, 상태(위임 중 / 만료 임박)를 본다 ② 상세에서 맡긴 일 5개를 본다 — 앱 사용자는 보기만, 서면·보호자 동의는 담당자가 스위치로 바꾸고 보호자에게 문자 ③ `[기간 연장 요청]` `[해지]` ④ "위임으로 한 일"(날짜·담당자·한 일) 기록을 본다 ⑤ "받은 요청" 탭에서 앱 사용자가 보낸 요청(새 연결 / 범위 변경)을 `[수락하고 연결]` 또는 `[거절]`.
- 업무 규칙: 끝나기 30일 전 "만료 임박", 위임으로 한 일은 본인·가족도 본다.
- 필요한 것: 대리 행위 기록(지금은 요청의 처리자만 남는다), 만료 스케줄러, 사용자 앱 쪽 위임 화면.

**O-35+ 담당자 간 기간 대리** (중*, 미구현) — (O-DLG-01 담당자 간 위임)
- 기본 흐름(명세): ① 방식 `[기간 동안 대리 | 완전히 이관]` ② 받는 담당자(같은 기관) ③ 대상(전체 / 골라서) ④ 시작·끝 ⑤ 맡길 일 ⑥ `[지정하기]` → 관리 대상에게 알림.
- 필요한 것: "완전히 이관"은 O-18+로 있다. 기간 대리는 기간 동안 두 담당자가 함께 볼 수 있게 하는 권한 검사가 필요하다.

**O-36+ 기관 공고 3종** (상*, 일부) — (O-POST-05·07·08)
- 목적: 특정 대상이 아니라 기관 이름으로 동네에 올리는 공고를 한곳에서 관리한다.
- 기본 흐름(명세): ① `[+ 공고 올리기]` → 종류 고르기 창 ② 종류별 입력 — 봉사자 모집(제목, 도움 종류, 날짜, 시간, 인원 1~2명, 할 일, 반복 한 번·매주·격주) / 단체 봉사(제목, 할 일, 날짜, 시간, 장소, 모집 인원, 준비물, 개인만·동아리도) / 해 드려요(어떤 도움, 내용, 가능한 때, 받을 수 있는 인원, 대상 누구나·65세 이상·혼자 사는 분, 신청 앱·전화, 노출 1km·3km·구 전체) ③ 올리기 ④ 카드 목록에서 종류 탭, 상태(모집 중 / 신청 받는 중), 신청/모집 막대, `[신청 보기]` `[마감]`.
- 업무 규칙: BR-034(안) — 봉사자 모집·단체 봉사는 봉사자 적립·차감 없음, 해 드려요는 적립·차감 없음.
- 지금 있는 것: 단체 봉사(모집형, 2~50명)만 O-07로 있다.
- 필요한 것: 봉사자 모집(1~2명)을 단체 봉사 인원 하한을 풀어 만들지 1:1 공고로 풀지 결정(M-07), 해 드려요(주민이 신청하는 반대 방향)의 새 흐름, 시간 재원 결정(M-04·M-05), 격주 반복.

**O-37+ 기관 공고 신청 처리** (상*, 미구현) — (O-POST-01 기관 공고 신청 탭, O-POST-09)
- 기본 흐름(명세): ① 요청 관리의 "기관 공고 신청" 탭에서 처리할 일 / 확정 / 완료와 종류 칩으로 본다 ② 신청을 열어 신청자 프로필, 함께 오는 인원, 메시지를 본다 ③ 봉사자 모집·단체 봉사는 `[거절]` `[수락]`(수락하면 확정, 당일 기관에서 QR, 봉사자 적립) ④ 해 드려요는 방문 날짜·시간을 넣고 `[일정 정해 확정]` 또는 `[어려워요]` ⑤ 신청자에게 알림.
- 필요한 것: 지금 단체 봉사는 선착순이라 신청 상태(신청 → 확정 → 완료, 거절)가 없다. 참여자 표에 상태와 수락 API, 기관 QR 체크가 필요하다.

**O-38+ 자격 미리 보기·연계 KPI ✨** (중*, 미구현) — (O-PUB-01·02)
- 기본 흐름(명세): 공공 서비스 요청 상세에서 "나이·가구로 본 대상 가능성"과 "확인할 것(기초연금 수급, 장기요양 등급)"을 근거(관리 대상 정보, 공공 서비스 DB)와 함께 본다. 목록 위에 새 요청 / 진행 중 / 이번 달 완료 / 연계 많은 서비스 네 칸.
- AI가 하는 일(안): 확인할 것 문장. 코드가 하는 일(안): 나이·가구와 서비스 대상 조건 견주기, 숫자 세기.
- 필요한 것: 가구 정보(O-31+), 공공 서비스 목록에 대상 조건을 견줄 수 있는 칸, "판정"이 아니라 "확인할 것"으로 읽히는 문구(NFR-012). KPI 네 칸은 지금 자료로도 만들 수 있다.

**O-39+ 추천 조치·안부 Top 3 ✨** (중*, 일부) — (O-RPT-01·02, O-HOME-01)
- 기본 흐름(명세): 홈에 "먼저 안부를 물어볼 분 Top 3"(순위, 이름·나이, 이유 한 줄, 근거: 최근 4주 일지·요청·취소). 리포트에 "이번 주 요약"(돌봄 완료율, 활동이 줄어든 분, 특보 영향), 대상별 4개월 막대, 도움과 요청 변화, 추천 조치(안부 전화 / 동행 공고 추가 / 공공 서비스 연계) `[하기]` → `✓ 했어요`.
- 지금 있는 것: 우선순위·동향 요약(O-10), 홈의 "살펴볼 대상"(O-21+).
- 필요한 것: 추천 조치를 고르는 규칙과 처리 기록, Top 3 카드, 주간 요약(주간 브리핑 O-20+를 다시 쓸 수 있다).

**O-40+ 담당자 정보 패널·알림 드롭다운** (하*, 일부) — (O-HOME-02·03)
- 기본 흐름(명세): 프로필(이름, 직무, 가린 연락처), 소속 기관(이름·종류·주소·승인일), 알림 스위치(새 제안·수락 / 일지 도착 / 운영자 특보), 공지사항·비밀번호 변경·로그아웃. 상단 🔔 드롭다운에 알림 행과 `[모두 읽음]`.
- 지금 있는 것: 마이(O-29+), 알림 화면(C-05), 알림 설정 5종.
- 필요한 것: 직무 칸, 기관 정보 표시, 특보·일지 알림을 끄는 스위치(지금은 끌 수 없는 종류다).

**O-41+ 기관 공고 문장 다듬기 ✨** (하*, 미구현) — (O-POST-08) — 기관 공고 쓰기의 `[AI로 문장 다듬기]`. 대리 공고 정리(`/ai/tidy-post`)를 다시 쓸 수 있다. O-36+가 먼저다.

**O-42+ 담당자 PC 화면 틀** (상*, 미구현) — (명세 1절)
- 요구: 1280px 이상에서 왼쪽 메뉴([돌봄] 홈 / 관리 대상 / 돌봄 편성표 / 요청 관리 / 공공 서비스 연계 · [기관 공고] 기관 공고 / 기관 행사 · [관리] 권한 위임 / 리포트 · 로그아웃), 상단 바(제목, 날짜, 알림, 프로필), 색 초록 `#4FAE96`. 원칙: 목록 + 상세 한 화면, 작은 일은 그 자리에서, 입력은 오른쪽 패널, 고르기는 가운데 창, AI 결과는 보라색 카드(✨ 제목 + 내용 + "근거 · …"). 900px 아래에서는 메뉴가 위로, 두 칸이 한 칸으로.
- 지금 있는 것: 같은 기능의 모바일 모양 화면과 서버 API. 화면 틀만 새로 만들면 O-01~O-29+는 API를 그대로 쓸 수 있다.
- 필요한 것: PC용 레이아웃과 화면 9개 메뉴, 화면마다 목록 + 상세로 다시 짜기, 용어 통일("도움 대상" → "관리 대상").

### 3.4 운영자

**A-01 운영 대시보드** (상)
- 출력: 상단 네 칸(이번 달 활동, 매칭률, 신규 가입/총 가입자, 등록 기관 수), 주별 수요·공급, 처리할 일(기관 신청·담당자 계정·신고·미답변 문의·카테고리 건의) → 눌러서 이동.
- API: `/admin/dashboard`, `/admin/analytics`. 남은 것: PC 명세는 넷째 칸이 "시간 발행·소비"라 계약서 7.19와 다르다(요구사항 정의서 C-06).

**A-02 봉사 유형 리포트 ✨** (중) · **A-04 계절별 봉사 리포트 ✨** (하)
- AI: 해석 문장 한 단락. 코드: 비율·분포·월별 집계, 다음 계절 예상 수요(그 계절 수요 × 최근 추세, 0.5~2.0으로 자름).
- API: `/admin/stats/types`, `/admin/stats/season`, `/admin/stats/by-type`.

**A-05 시간 은행 재정 추계 ✨** (상)
- 목적: 시간 은행이 몇 년 뒤에도 버틸 수 있는지 본다.
- 흐름: ① 연도(올해, 1·3·5·10년 뒤)·동네별 공급·수요·부족을 본다 ② 위험 동네와 이유를 본다 ③ 가정값 표에서 값마다 "기록"인지 "가정"인지 본다 ④ 이번 달 요약을 만든다(저장됨).
- AI: 위험 동네 월간 요약 문장. 코드: 나이대 8개 × 동네 코호트 계산, 위험도.
- API: `/admin/forecast`, `/admin/forecast/summary`, `/admin/forecast/summaries`.
- 남은 것: 시연 자료는 회원이 적어 대부분 가정값이다. 사망·전출·동네 이동은 모형에 없다.

**A-06 정책 시뮬레이션 ✨** (상)
- 흐름: ① 문장을 넣는다(예: "20대 가입이 월 30명 늘면") ② AI가 조정 값(가입 수·이탈률 배수·1인당 공급·수요 시간)으로 바꾼다 ③ 코드가 범위를 자르고 다시 계산 ④ 전·후 그래프와 바뀐 변수를 본다.
- 예외: 못 알아들으면 직접 값을 넣는다. 키가 없으면 가입 수·이탈률·시간 문장만 알아듣는다.
- AI: 자연어 → 조정 값. 코드: 형식·범위 검사(가입 ±1000명, 배수 0~5, 시간 ±20), 재계산.
- API: `/admin/forecast/simulate`. 남은 것: AI 추천 정책 3개·추계와 한 화면·공지로 보내기는 A-27+.

**A-07 대응 추천 ✨** (중) — 부족이 큰 동네·카테고리 5개와 요청이 많은 시간대는 코드가 고르고, 모집 문구만 AI가 다듬는다. API `/admin/recruit-drafts`.

**A-08 특보 알림 리포트 ✨** (중, 일부)
- 흐름: ① 특보를 받아 오거나 직접 넣거나 표본을 만든다 ② 영향 지역의 관리 대상 수, 80대 이상 수, 예정 활동, 담당자를 본다 ③ 요약과 권장 조치를 읽는다 ④ 전달(A-09).
- AI: 리포트 요약·할 일 문장. 코드: 위험 지역·대상 수 세기.
- API: `/admin/weather/alerts`, `/admin/weather/fetch`, `/admin/weather/alerts/sample`, `/admin/weather/alerts/{id}/refresh`.
- 남은 것: 기상청 호출은 키가 있을 때만이고 응답 읽는 부분이 짐작이다. 실제 호출로 확인 못 했다. 주기적으로 받아 오지 않는다. 모든 동네를 한 기상 구역으로 본다.

**A-10 기관 신청 승인** (상)
- 흐름: ① 대기 목록에서 기관을 연다 ② 주소·담당자·증빙 파일을 본다 ③ 승인 → 첫 담당자 계정과 임시 비밀번호(이 화면에서만 보임) 발급, 또는 사유를 적어 반려.
- API: `/admin/orgs/{id}/approve`, `/admin/orgs/{id}/reject`.

**A-20+ 이상 적립 패턴 점검 ✨** (중*) — 묶음 찾기와 근거 숫자(횟수, 평균 시간, 시간대, 일지 길이, 같은 일지 문장)는 코드, 설명 글만 AI(단정 금지). 보류·해제는 운영자가 누른다. API `/admin/anomalies`, `/admin/ai/anomalies`.

**A-22+ 교육 상황·가상 상대 관리 ✨** (하*) — 신고·경고 메시지·전달 메모에서 사례를 코드가 세고, AI가 역할극 상대 초안(가명, 3턴)을 만든다. 형식이 틀리면 규칙 틀을 쓴다. 등록은 운영자가 고쳐서 한다. API `/admin/edu/situations`, `/admin/personas`, `/admin/ai/persona-cases`, `/admin/ai/persona-draft`.

**A-24+ 신고 정리 ✨** (중*) — 심각도는 코드 규칙이 바닥(신체 접촉·금전 요구·위협 = 높음)이고 AI는 올리기만 할 수 있다. 한 줄 요약과 비슷한 지난 건을 붙인다. 제재는 운영자가 한다. API `/admin/ai/report-triage`.

**A-25+ 문의 답변 초안 ✨** (하*) — 근거(이용 규칙 요약, 맞는 공지, 그 사용자의 통장 최근 5건, 관련 요청 상태)는 코드가 모으고 초안 글만 AI. 보내지 않는다. API `/admin/ai/inquiries/{id}/draft`.

**A-26+ 이용 리포트 토글·탭 ✨** (중*, 일부) — 도움 요청/봉사 가능 토글에 따른 나이별·계절별·지역별 통계는 있다(`/admin/stats/by-type`). PC 명세의 다섯 탭, 지역 칩, 회원·공고 탭, 탭마다 AI 해석은 없다.

**A-27+ AI 추천 정책·추계 합치기 ✨** (중*, 미구현) — PC 명세 A-03: 재정 추계와 시뮬레이션을 한 화면으로, AI 추천 정책 3개(이름, 근거, 예상 역전 시점 변화)를 눌러 바로 시뮬레이션, 결과의 모집 문구 초안을 `[공지로 보내기]`. 추천 정책을 공지까지 바로 보낼지는 회의 항목(M-09).

**A-28+ 운영 분석 ✨** (중*) — 부족한 카테고리(수요·공급 차이는 코드 값), 맞춰지지 않은 공고, 6개 카테고리에 안 맞는 문장에서 새 카테고리 후보를 요약한다. 1시간 캐시. API `/admin/insights`.

## 4. AI 기능 요약

AI는 서버의 `AiClient` 한 곳에서만 부른다. 공급자는 환경변수로 고르고(Gemini → Anthropic → 규칙 순) 키가 없으면 규칙 모드다. **실제 AI(키 있음)로 확인된 기능은 하나도 없다** — 적용 결과 문서 모두 "규칙 모드로만 확인"이고 이번에도 부르지 않았다.
