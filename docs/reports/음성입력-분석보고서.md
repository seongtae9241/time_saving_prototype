## 0. 한눈에 보기

| 질문 | 결론 |
|---|---|
| 왜 필요한가 | 봉사받는 사용자 중 어르신은 작은 화면에 날짜·시간·장소를 하나씩 입력하기 어렵다. 말로 하면 1분 안에 요청서가 만들어지고, 화면 입력은 "확인" 버튼 하나만 남는다 |
| 프로토타입 상태 | 마이크 버튼이 4곳(공고 작성 `wn`, AI 도움 추천 `rec`, 교육 역할극 `rp`, 클래스 열기 `cn`)에 있지만, 모두 "음성 입력은 테스트 중이에요" 안내 시트만 뜨는 **모의 동작**이다 |
| 어떻게 만드나 | **1단계(지금 구현 중)**: 브라우저 음성 인식(Web Speech API) → 받아쓴 글 → 백엔드 `AiClient`가 요청서 JSON으로 정리 → 소리로 읽어 주고 큰 버튼으로 확인. **2단계**: 서버 음성 인식(STT) 붙이기. 브라우저를 가리지 않고, 사투리 정확도를 높인다. **3단계**: 스마트폰이 없는 어르신을 위한 전화(ARS) 접수 |
| AI가 분석할 것 | 요청서 칸 채우기(날짜·시간·길이·장소·카테고리·내용·반복·주의사항), 말의 의도 구분(새 요청/단골 요청/취소·변경/확인/질문/위급), 금지 요청 판정, 난이도·예상 시간, 개인정보·연락처 가리기, 위급 신호 감지, 칸마다 확신도 → 되묻기 |
| 꼭 지킬 것 | AI 결과로 **자동 등록하지 않는다**(요청서를 보여 주고 버튼으로 확정, B-03). 숫자·규칙 검사는 코드가 한다. 녹음 원본은 저장하지 않는다. 건강 관련 말은 진단하지 않고 최소한만 남긴다 |

## 1. 누가, 어디서 말로 입력하나 — 음성 입력 후보 전체

요구사항과 프로토타입의 입력칸을 모두 훑어, 말로 받을 가치가 있는 곳을 골랐다. "우선순위"는 어르신 사용성 효과와 구현 난이도를 함께 본 것이다.

| 우선 | 화면·기능 | 요구사항 | 말하는 사람 | 말로 받으면 좋은 이유 | AI가 할 일 |
|---|---|---|---|---|---|
| ★★★ | **도움 요청 공고 쓰기 ("말로 요청하기")** | B-02, B-05, B-07~B-10 | 봉사받는 어르신 | 입력칸이 가장 많고, 가장 어려운 화면 | 요청서 칸 채우기 + 되묻기 + 금지 필터 + 난이도 |
| ★★★ | 담당자 대리 공고 쓰기 | C-04 | 담당자 | 어르신과 통화하면서 들은 내용을 바로 말로 옮김 | 위와 같음 + 독거노인 별칭 연결 |
| ★★★ | 활동 일지 한 줄 기록 | B-24 | 봉사자 | 활동 직후 걸어가면서 말로 남김 | 일지 정리(기존 `log-tidy`) + 개인정보 가리기 |
| ★★☆ | 단골에게 요청하기 | B-14, C-06 | 어르신·담당자 | "지난번 그 하늘이 학생 또 와 줬으면" | 단골 이름 찾기 → 단골 요청으로 바로 연결 |
| ★★☆ | AI 도움 추천·공공 서비스 질문 | P-01, 프로토타입 `recommend`/`public` | 어르신 | 질문을 글로 쓰기 어려움 | 상황 이해 → 카테고리 추천 / 공공 서비스 검색 |
| ★★☆ | 활동 확인·평가 | B-23, B-38 | 어르신 | "네, 잘 해 주고 갔어요" 한마디로 확인 | 확인 의사 판정, 별점·태그 추출(최종은 버튼) |
| ★★☆ | 봉사 가능 공고 쓰기 | B-04 | 봉사자(어르신 봉사자 포함) | 60~70대 봉사자도 많음(프로토타입 최미경 60대) | 요청서 칸 채우기(가능 시간 범위·카테고리 여러 개) |
| ★☆☆ | 요청·제안 메시지 | A-08, C-09 | 모두 | 짧은 답장("네 10시까지 갈게요") | 받아쓰기만 + 연락처·금전 요구 경고 |
| ★☆☆ | 1:1 문의·신고 | B-36, B-48 | 모두 | 상황 설명이 길다 | 문의 유형·신고 유형 분류, 제목 만들기 |
| ★☆☆ | 동네 클래스 열기 | 프로토타입 `cls_new` | 어르신 선생님 | "김치 담그는 법 알려 줄게" | 수업 단계(steps)·준비물·주의사항 정리, 난이도(허용/주의) |
| ★☆☆ | 교육 역할극 대답 | 프로토타입 `edu_rp` | 봉사자 | 실제 현장처럼 말로 대답하는 연습 | 기존 역할극 판정(연락처·금전·신체 돌봄·개인정보 위반) |
| ★☆☆ | 담당자 방문 메모 | C-02 | 담당자 | 방문 직후 메모 | 메모 정리 + 민감정보(이름·주소·연락처) 가리기 |

**1차 범위:** ★★★ 3개("말로 요청하기", 담당자 대리 작성, 활동 일지). 사용자 요청으로 "말로 요청하기"는 지금 개발 중이다. 화면 컴포넌트 하나로 만들어 위 표의 다른 화면에도 그대로 붙일 수 있게 한다.

## 2. 구현 방식 비교 — 음성을 글로 바꾸는 방법(STT)

Claude API는 텍스트·이미지를 입력으로 받는 구조라, 음성은 먼저 다른 방법으로 글로 바꾼 뒤 `AiClient`에 넘긴다. 즉 **"음성 → 글(STT)"과 "글 → 요청서(LLM)"는 별개의 두 단계**다.

| 방식 | 장점 | 단점 | 비용 | 판단 |
|---|---|---|---|---|
| **A. 브라우저 음성 인식 (Web Speech API)** | 설치·서버 없음. 실시간으로 글자가 보임. 개발이 가장 빠름 | 브라우저마다 지원이 다름(크롬·엣지·사파리·삼성 인터넷 계열은 되고 파이어폭스는 안 됨 — 출시 전 실기기 확인 필요). 크롬은 음성을 브라우저 회사 서버로 보내 처리하므로 처리방침에 알려야 함. 사투리·작은 목소리 정확도를 우리가 조절할 수 없음 | 0원 | **1단계 채택** |
| B. 서버 STT (녹음 파일 → 음성 인식 API) | 브라우저를 가리지 않음. 한국어 특화 업체를 고르면 사투리·고령자 발화 정확도가 높음. 단어 사전(동네 이름·병원 이름) 등록 가능 | 녹음 업로드·서버 연동 개발. 분당 과금. 개인정보 위탁·국외 이전 고지 | 분당 과금 (업체별 단가는 계약 전 확인) | **2단계** |
| C. 기기 안에서 인식 (브라우저용 Whisper 등) | 음성이 밖으로 나가지 않음. 비용 0원 | 모델 내려받기가 수십~수백 MB. 오래된 휴대폰에서 느림 → 어르신 기기에 맞지 않음 | 0원 | 보류 |
| D. 전화(ARS) 접수 | 스마트폰·앱이 없는 어르신도 쓸 수 있음. B-42(AI 음성 전화 안내)와 같은 통로 | 전화망 업체 계약, 본인 확인 방법 필요 | 통화료 + STT | **3단계**(사업 확장 때) |

**설계 원칙:** STT는 바뀔 수 있으니 백엔드에 `SttClient` 한 곳만 두고(AI가 `AiClient` 한 곳을 거치는 것과 같은 원칙), 어떤 방식으로 받든 결과는 **같은 글 → 같은 `POST /api/ai/post-chat`**으로 흘러가게 한다. 그러면 B·D를 붙여도 요청서 분석 로직은 그대로 쓴다.

## 3. "말로 요청하기" 동작 흐름 (1단계, 지금 구현 중)

```
[홈] 큰 마이크 카드 "말로 요청하기"
   │ 누르기
   ▼
① 듣기: 브라우저 음성 인식(ko-KR). 말하는 동안 글자가 실시간으로 보이고, 마이크가 숨 쉬듯 움직인다
   │ 2~3초 조용하면 자동 종료, 또는 "다 말했어요" 버튼
   ▼
② 받아쓴 글 보여 주기 (직접 고칠 수 있음)
   │
   ▼
③ POST /api/ai/post-chat { type:'NEED', inputMode:'voice', messages:[…] }
   │
   ├─ done=false → 빠진 것 하나만 소리로 되묻기 ("몇 시쯤 오면 좋으세요?") → ①로 (대화 이어 가기)
   ├─ filter=BLOCK → 이유 + 공공 서비스 안내를 크게 보여 주고 읽어 줌 (B-09, P-01)
   └─ done=true  → ④
   ▼
④ 요청서 카드: 날짜·시간·장소·카테고리·내용·예상 시간·난이도를 큰 글씨로 보여 주고 summarySpeech를 읽어 줌
   "11월 18일 화요일 오후 2시부터 2시간, 병원 동행 요청서를 만들었어요. 올릴까요?"
   │
   ├─ [이대로 올리기] → POST /api/posts (서버가 일정 규칙·금지 필터를 한 번 더 검사)
   ├─ [고칠래요] → 고칠 칸만 다시 말하기 또는 손으로 고치기
   └─ [다시 말하기]
```

어르신 화면 원칙:
- 버튼은 높이 64px 이상, 글씨 크게(글자 크기 설정 반영). 한 화면에 질문 하나.
- 되묻기는 **최대 3번**. 그 뒤에도 비면 말 대신 큰 선택 버튼(예: "오전 / 오후", 날짜 달력)을 보여 준다.
- 소리로 읽어 주기는 느리게(속도 0.9). 끄는 버튼을 둔다.
- 음성 인식이 안 되는 기기이거나 마이크 권한을 거부하면 "이 기기에서는 음성 입력이 안 돼요. 아래에 적어 주세요" + 큰 입력칸으로 **같은 흐름**을 탄다.
- **절대 자동 등록하지 않는다.** 마지막은 항상 사람이 누르는 버튼(B-03 "공고 요약을 보여 주고 버튼을 눌러서 등록").

## 4. AI에게 분석시킬 내용 — 항목별 상세

받아쓴 글 한 덩어리에서 아래를 뽑는다. **"누가 결정하나"** 열이 중요하다. AI는 추출·제안만 하고, 숫자 계산·규칙 판정·최종 확정은 코드와 사람이 한다.

### 4.1 말 다듬기 (전처리)

| 분석 | 예 | 누가 결정 |
|---|---|---|
| 군말 제거 | "어… 그러니까 음 장 좀" → "장 좀" | AI(규칙 모드는 군말 목록) |
| 받아쓰기 오류 보정 | "정형외가" → "정형외과", "행복똥" → "행복동"(동네 이름 사전과 대조) | AI + 동네·기관 사전 |
| 사투리·옛 표현 이해 | "장 좀 봐 줄 텨?", "모레 아척에" → 모레 아침 | AI |
| 한글 숫자 → 숫자 | "두 시 반" → 14.5, "한 시간 반" → 1.5 | 코드(파서) + AI |

### 4.2 요청서 칸 채우기 (B-02, B-05, B-07, B-10)

| 칸 | 말 예시 | 뽑는 값 | 주의 |
|---|---|---|---|
| 날짜 | "다음 주 화요일", "모레", "18일" | `2026-11-17` | 상대 날짜는 **오늘 날짜를 프롬프트에 넣어** 계산. 지난 날짜면 되묻기 |
| 시작~끝 시각 | "오후 두 시부터 네 시까지", "점심 먹고" | 14.0~16.0 | "두 시"처럼 오전·오후가 없으면 1~6시는 오후로 가정하고 **읽어 주며 확인** |
| 활동 시간 | "두 시간 정도", "한나절" | 2.0 | 30분 단위로 반올림, 4시간 넘으면 나눠 올리자고 안내(B-10) |
| 장소 | "행복동", "햇살정형외과", "우리 집" | 동 단위 지역 + 장소 설명 | "우리 집"은 공고에 **주소를 쓰지 않고** 동만(B-13 취지). 상세 장소는 수락 뒤 메시지로 |
| 카테고리 | "병원 같이 가" → 동행, "쌀 사다" → 장보기 | 6개 중 1개(복수면 최고 등급, B-29) | 애매하면 후보 2개를 버튼으로 |
| 세부 내용·제목 | 말 전체 | 제목 15자 안팎 + 내용 1~2문장 | 존댓말로 다듬기 |
| 반복 | "매주 목요일마다" | 반복 규칙(B-06) | 몇 주인지 되묻기 |
| 방문 주의사항 | "무릎이 아파서 천천히", "개가 있어" | 주의사항 칸 | 건강 관련은 4.6 참고 |
| 희망 조건 | "지난번 그 학생", "여자분이면 좋겠어" | 단골 후보 / 메모 | 단골이면 **단골 요청(B-14)으로 연결**. 성별 같은 조건은 메모로만 남기고 차별 필터로 쓰지 않음 |

### 4.3 말의 의도 구분

같은 마이크로 여러 가지를 말할 수 있으므로, 먼저 무엇을 하려는 말인지 나눈다.

| 의도 | 예 | 연결되는 기능 |
|---|---|---|
| 새 도움 요청 | "장 좀 봐 줄 사람" | 요청서 만들기(B-05) |
| 단골에게 요청 | "미경 씨 또 와 줬으면" | 단골 요청(B-14) |
| 기존 요청 변경·취소 | "목요일 거 취소해 줘" | 내 활동 → 취소(B-25, 24시간 규칙 안내) |
| 활동 확인 | "응, 왔다 갔어. 잘해 줬어" | 확인 버튼 화면으로 안내(B-23). 확정은 버튼 |
| 질문 | "병원비 지원 같은 거 없나?" | 공공 서비스 안내(P-01) |
| 이야기·외로움 | "그냥 심심해서" | 말동무 공고 제안 |
| 위급 | "숨이 차", "넘어졌어" | 4.5 위급 대응 |

### 4.4 금지 요청 판정 (B-09) · 난이도 (B-08, B-27)

- **금지 필터**: 허용 / 주의 / 불가. 불가는 신체 돌봄(목욕·기저귀·파스), 의료 행위(약 먹이기·주사), 금전 관리(통장·카드·현금), 위험 작업. 불가면 이유와 공공 서비스(P-01 DB에 있는 것만)를 안내한다. 말로 들어온 요청은 단어가 흐트러져 있으므로 **AI 판정 + 규칙 키워드 검사를 함께** 돌린다. 둘 중 하나라도 불가면 불가로 본다.
- **난이도**: 신체 부담·책임·위험·전문성·이동·접근성 요소로 등급(기본·수고·책임)과 근거를 제안한다. 가중치(1.0/1.2/1.5)와 예상 시간 계산은 코드가 한다.

### 4.5 안전 신호 감지

| 신호 | 예 | 대응 | 하지 않는 것 |
|---|---|---|---|
| 위급 상황 | "쓰러졌어", "숨이 안 쉬어져" | 요청서 흐름을 멈추고 **119 전화 버튼**·응급안전안심서비스 안내를 크게. 독거노인은 담당자 알림 | 증상 판단·진단 |
| 위기 발언 | 삶을 놓고 싶다는 말 | 상담 전화(109 자살예방상담전화 등) 안내 + 담당자·운영자 알림 정책은 법무 검토 뒤 확정 | 상담을 AI가 대신하기 |
| 금전 요구·사기 의심 | "돈 좀 빌려줄 사람" | 금전 관리 불가 안내(B-34 돈 연동 없음) | — |

### 4.6 개인정보 가리기

| 정보 | 예 | 처리 |
|---|---|---|
| 전화번호·계좌·주소 상세 | "공일공 일이삼사…", "○○아파트 102동" | 공고 본문에서 지우고 "수락 뒤 메시지로 안내돼요"로 대신(A-08 연락처 교환 금지, B-13) |
| 실명(독거노인) | 담당자가 "이순례 할머니" | 담당자 화면에서는 별칭으로 바꿔 저장(C-02 별칭만) |
| 건강 정보(민감정보) | "무릎 수술했어", "치매 초기" | 방문에 필요한 최소 문장("천천히 걸어 주세요")으로 줄이고 **병명은 저장하지 않음**. 저장 전에 어르신에게 읽어 주고 확인받기 |

### 4.7 확신도와 되묻기

AI는 칸마다 `confidence`(높음/보통/낮음)를 함께 돌려준다. **낮음이면 그 칸만 되묻고, 보통이면 읽어 주며 확인한다.** 날짜·시각처럼 틀리면 곤란한 칸은 높음이어도 마지막 확인에서 꼭 읽어 준다.

### 4.8 AI 응답 형식 (계약 — `POST /api/ai/post-chat`)

```json
{
  "reply": "몇 시쯤 오면 좋으세요?",
  "done": false,
  "intent": "NEW_REQUEST",
  "draft": {
    "date": "2026-11-17", "startHour": 14.0, "endHour": 16.0, "estHours": 2.0,
    "area": "행복동", "categories": ["동행"],
    "title": "정형외과 진료 동행", "detail": "햇살정형외과 진료 후 약국 들르기",
    "caution": "무릎이 불편하셔서 천천히 걸어 주세요",
    "repeat": null,
    "summarySpeech": "11월 17일 화요일 오후 2시부터 2시간, 병원 동행 요청서를 만들었어요. 올릴까요?"
  },
  "confidence": { "date": "high", "time": "medium", "area": "high", "category": "high" },
  "missing": [],
  "filter": { "level": "ALLOW", "reason": "", "alternatives": [] },
  "difficulty": { "level": "RESPONSIBLE", "weight": 1.5, "reason": "병원 이동·접수 동행으로 책임이 큼", "estEarn": 3.0 },
  "safety": { "emergency": false, "piiRemoved": ["phone"] },
  "source": "ai"
}
```
- `source`가 `rule`이면 API 키 없이 규칙 파서로 만든 결과다. 키가 없어도 시연·개발이 되도록, 규칙 파서도 상대 날짜·한글 숫자·카테고리 키워드를 실제로 처리한다(개발 중, 단위 테스트 포함).
- `intent`, `confidence`, `safety`는 이번 보고서에서 새로 제안하는 필드다. 계약서 7절에 반영할 대상이다.

## 5. 프롬프트 설계 요점

1. **오늘 날짜·요일**과 사용자의 활동 지역(동)을 시스템 프롬프트에 넣는다. 상대 날짜를 정확히 계산하기 위해서다.
2. "음성 받아쓰기라 띄어쓰기·오타·군말이 섞여 있다"고 알려 준다.
3. 되묻기는 **존댓말로, 한 번에 하나, 소리로 읽기 좋은 1~2문장**으로 하게 한다.
4. 출력은 위 JSON만 쓰게 한다. 서버는 JSON을 검증하고, 실패하면 규칙 파서 결과로 대신한다.
5. 금지: 진단·건강 판단, 공공 서비스 자격 판정, DB에 없는 서비스 지어내기, 연락처를 공고에 남기기.
6. 비용: 요청서 1건에 되묻기를 포함해 AI 호출 2~4번, 짧은 대화라 1건당 몇 원 수준(Haiku 기준, 정확한 단가는 운영 전 측정). 대화 기록은 최근 몇 턴만 보낸다.

## 6. 개인정보·법무 체크리스트

- [ ] **녹음 원본은 저장하지 않는다.** 1단계는 브라우저가 처리하므로 서버에 음성이 오지 않는다. 2단계 서버 STT는 인식 직후 메모리에서 버린다.
- [ ] 처리방침에 알릴 것: 음성 인식 처리 주체(브라우저 제공사 또는 STT 업체), AI 처리 업체(국외 이전 여부), 받아쓴 글의 보관 기간.
- [ ] 받아쓴 원문은 요청서가 만들어지면 지우고, 정리된 요청서만 저장한다(최소 수집).
- [ ] 건강 관련 말은 민감정보라 병명을 저장하지 않는다(4.6).
- [ ] 마이크 권한은 버튼을 누를 때만 요청한다. 앱을 열자마자 묻지 않는다.
- [ ] 담당자 대리 작성 때 어르신 실명·주소는 별칭·동으로만 남긴다.

## 7. 정확도 검증 계획

| 단계 | 방법 | 기준 |
|---|---|---|
| ① 문장 테스트(0원) | 어르신 말투 문장 50개(군말·사투리·상대 날짜·한글 숫자·금지 요청·위급 포함)를 규칙 파서 단위 테스트로 | 날짜·시각·카테고리 정답률 90% 이상, 금지 요청 놓침 0건 |

| ④ 실제 사용자 | 주민센터·경로당 어르신 5~10명에게 "장보기 요청을 말로 해 보세요" | 도움 없이 등록 완료율, 걸린 시간(목표 2분 안), 고친 칸 수 |

## 8. 단계별 일정 제안

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | 브라우저 음성 인식 + `post-chat`(voice 모드) + 소리로 읽어 주기 + 큰 버튼 확인. 홈 "말로 요청하기", 공고 쓰기, 담당자 대리 작성 | **개발 중**(사용자 요청 반영) |
| 1.5단계 | 같은 컴포넌트를 활동 일지·AI 추천·공공 서비스 질문·확인·문의/신고에 붙이기. `intent`·`confidence`·`safety` 필드 반영 | 다음 |
| 2단계 | `SttClient` + 서버 STT(한국어 특화 업체 비교 후 선택), 동네·병원 이름 사전 | 업체 선정·비용 확인 필요 |
| 3단계 | 전화(ARS) 접수: 전화 → STT → 같은 요청서 흐름 → 담당자 또는 본인 확인 | 사업 확장 때 |

## 9. 정해야 할 것 (팀 결정 필요)

1. 2단계 서버 STT를 할지와 업체(비용·정확도·개인정보 위탁 조건 비교).
2. 위기 발언 감지 시 담당자·운영자에게 알릴지(법무 검토).
3. 받아쓴 원문을 디버깅용으로 며칠 보관할지, 아예 저장하지 않을지(제안: 저장 안 함).
4. 전화(ARS) 접수를 사업 범위에 넣을지.
