# 2026-11-16 담당자 추가 기능 API (권한 위임 · 기관 공고 3종 · 홈 봉사자 현황 · AI 도우미)

- 기준 프로토타입: `docs/prototypes/proto-2026-11-16-기관담당자-PC.html`
- 대상: `docs/design/contract.md` 7.22 "5판에 있지만 넣지 않은 것" 가운데 서버가 없어서 못 넣은 4가지의 **서버 쪽**. 화면(`frontend/`)은 아직 없다.
- 이 문서만 보고 화면을 붙일 수 있게 적었다. 실제 응답 예시는 필요한 칸만 줄여서 적었다.
- 코드: `backend/src/main/java/com/timesavings/` 의 `web/DelegationController` · `web/OrgNoticeController` · `web/OrgExtraController`, `service/DelegationService` · `OrgNoticeService` · `OrgVolunteerService` · `OrgAssistantService`, `ai/OrgAssistantAi`. 테스트: `Org1116Test`, `ai/OrgAssistantAiTest`.

## 0. 공통

- 인증: `Authorization: Bearer <토큰>`. `/api/org/**` 는 ORG 역할만(기존 `AuthInterceptor`). 사용자 쪽 주소(`/api/delegations/**`, `/api/org-notices/**`)는 로그인만 검사하고 역할은 각 API가 검사한다.
- 소유 검사: 관리 대상에 딸린 것은 **내가 담당하는 대상**(`elders.manager_id` = 나)만, 기관 공고는 **우리 기관**(`org_id` = 내 기관) 것만. 아니면 403.
- 오류 응답: HTTP 4xx + `{ "error": "사람이 읽는 문장", "code": "코드" }`. 공통 코드: `UNAUTHORIZED`(401), `FORBIDDEN`(403), `NOT_FOUND`(404).
- 날짜는 `2026-11-16`, 시각은 숫자(`14.5` = 14:30, 30분 단위).
- 결정은 사람이: 위임 등록·동의·회수, 신청 수락·거절, 마감, 참석 확인은 모두 버튼 API를 불러야 바뀐다. AI 도우미는 아무것도 바꾸지 않는다.
- 응답의 `link` 값 가운데 `/o/delegations`, `/o/notices`, `/my/delegations`, `/org-notices/:id` 는 **아직 없는 화면 경로(제안)** 다. 프론트에서 실제 경로를 정하면 서버 상수를 맞춘다(8장).

## 1. 권한 위임

관리 대상(또는 보호자)이 담당자에게 맡긴 일의 범위를 기록한다.

### 1-1. 값

**맡긴 일 범위(`scopes`)** — 프로토타입 `ALLSCOPE` 순서 그대로.

| 코드 | 화면 이름 |
|---|---|
| `POST_PROXY` | 대신 공고 |
| `ACCEPT_PROXY` | 대신 수락 |
| `LOG_CONFIRM` | 일지 확인 |
| `PUBLIC_SERVICE` | 공공 서비스 |
| `CHECK_IN` | 안부 확인 |

**동의 방법(`consentMethod`)** — 종류 코드와 날짜(`consentDate`)만 저장한다. 동의서 사진·PDF·서명·보호자 연락처는 받지도 저장하지도 않는다.

| 코드 | 이름 | 유효해지는 때 |
|---|---|---|
| `APP` | 앱 동의 | 본인이 앱에서 동의를 눌렀을 때(또는 본인이 보낸 연결 요청을 담당자가 수락했을 때) |
| `PAPER` | 서면 동의 | 담당자가 "동의를 받았음"을 체크(`consentConfirmed:true`)하고 등록했을 때 |
| `GUARDIAN` | 보호자 동의 | 보호자 계정이 있으면 보호자가 앱에서 동의를 눌렀을 때 / 계정이 없으면 담당자가 체크하고 등록했을 때 |

**상태(`status`)**

| 값 | `statusLabel` | 뜻 |
|---|---|---|
| `NONE` | 위임 없음 | 이 대상에 위임 기록이 없다(목록에서만 나온다) |
| `PENDING` | 동의 대기 | 앱·보호자 동의를 기다린다 |
| `ACTIVE` | 위임 중 / **만료 임박**(`expiringSoon:true`, 끝나는 날까지 30일 이하) | 유효 |
| `EXPIRED` | 만료 | 끝나는 날이 지났다(저장값이 아니라 날짜로 계산) |
| `REVOKED` | 회수됨 | 담당자 또는 본인·보호자가 회수 |
| `REJECTED` | 동의하지 않음 | 본인·보호자가 동의 요청을 거절 |

- 기간은 최대 1년(`PERIOD_TOO_LONG`). 자동 연장은 없다.
- 한 대상에 "동의 대기 또는 유효"한 위임은 하나뿐이다. 만료·회수·거절된 뒤에는 새로 등록한다.
- 보호자(`guardianUserId`)는 **본인 앱 계정과 가족으로 연결(수락됨)된 계정**만 고를 수 있다. 본인 앱 계정은 그 사람이 앱에서 "담당 기관 연결"을 요청해 수락된 적이 있을 때만 안다(담당자가 계정을 찾아 붙이는 기능은 없다).

### 1-2. 담당자 API

#### `GET /api/org/delegations` — 위임 목록 (O-DLG-01)
내 관리 대상(지원 중) 한 명당 한 줄.
```json
{
  "items": [
    { "id": 3, "elderId": 11, "displayName": "이순례 님", "ageGroup": "80대", "dong": "행복동",
      "consentMethod": "PAPER", "consentMethodLabel": "서면 동의", "consentDate": "2026-03-31",
      "scopes": ["POST_PROXY","ACCEPT_PROXY","LOG_CONFIRM","CHECK_IN"], "scopeCount": 4,
      "scopeItems": [ {"code":"POST_PROXY","label":"대신 공고","on":true}, {"code":"PUBLIC_SERVICE","label":"공공 서비스","on":false} ],
      "startDate": "2026-03-31", "endDate": "2027-03-30",
      "status": "ACTIVE", "statusLabel": "위임 중", "expiringSoon": false, "daysLeft": 134,
      "appLinked": false, "hasGuardianAccount": false, "guardian": null,
      "editableByManager": true, "canRevoke": true, "canAskExtend": false },
    { "id": null, "elderId": 14, "displayName": "오덕수 님", "ageGroup": "80대", "dong": "사랑동",
      "status": "NONE", "statusLabel": "위임 없음", "scopes": [], "scopeCount": 0, "appLinked": false, "expiringSoon": false }
  ],
  "counts": { "total": 4, "active": 3, "expiringSoon": 1, "expired": 0, "pending": 0, "none": 1, "requests": 1 },
  "scopes": [ {"code":"POST_PROXY","label":"대신 공고"} ],
  "consentMethods": [ {"code":"APP","label":"앱 동의"}, {"code":"PAPER","label":"서면 동의"}, {"code":"GUARDIAN","label":"보호자 동의"} ],
  "maxDays": 365, "soonDays": 30, "today": "2026-11-16",
  "notice": "위임 기간이 끝나기 30일 전부터 '만료 임박'으로 보여요. 본인(또는 보호자)에게 다시 동의를 받아 주세요."

```
- `counts.requests` = 답을 기다리는 "받은 요청" 수(탭 숫자).
- `editableByManager`: 앱 동의(`APP`)는 false — 프로토타입의 "앱을 쓰시는 분이라 본인이 앱에서만 바꿀 수 있어요".

#### `GET /api/org/delegations/{id}` — 위임 상세 (O-DLG-02)
목록 한 줄과 같은 칸 + 아래.
```json
{
  "history": [ { "id": 9, "delegationId": 3, "action": "SCOPE_CHANGED", "actionLabel": "맡긴 일 변경", "actorRole": "MANAGER",
                 "actorName": "박지원", "detail": "대신 공고 · 일지 확인 → 대신 공고 · 안부 확인", "at": "2026-11-16T10:12:00" } ],
  "acts": [ { "at": "2026-11-12T09:30:00", "scope": "POST_PROXY", "by": "박지원", "text": "병원 동행 공고를 대신 올림", "link": "/post/31" },
            { "at": "2026-11-10T14:00:00", "scope": "ACCEPT_PROXY", "by": null, "text": "11/14(토) 말동무·정서 일정을 확정", "link": "/requests/52" } ],
  "actsNote": "기록은 본인·가족도 볼 수 있어요. 일정 확정과 일지 확인은 누른 사람을 따로 저장하지 않아요."
}
```
- `history` = **변경 기록**(등록·동의·범위 변경·연장·연장 요청·회수·요청 수락/거절). `action`: `CREATED` `CONSENTED` `CONSENT_REJECTED` `SCOPE_CHANGED` `EXTENDED` `EXTEND_ASKED` `REVOKED` `LINK_ACCEPTED` `REQUEST_REJECTED`. `actorRole`: `MANAGER` `USER` `GUARDIAN`.
- `acts` = 프로토타입 "위임으로 한 일". 새로 저장하지 않고 기존 대리 공고·요청에서 읽는다(최근 10건). 일정 확정·일지 확인은 `by` 가 null 이다.
- 오류: 남의 대상 403.

#### `GET /api/org/elders/{elderId}/delegation` — 대상 한 명의 지금 위임 + 등록에 쓸 값
상세와 같은 칸(없으면 `status:"NONE"`) + `appLinked`, `guardianCandidates: [{userId, name, relation}]`, `canCreate`.
- O-DLG-03 에서 대상을 고르면 불러서: `appLinked` 가 false 면 "앱으로 동의 요청"을 고를 수 없게, `guardianCandidates` 가 비어 있으면 보호자 계정 고르기를 숨긴다.

#### `POST /api/org/delegations` — 새 위임 등록 (O-DLG-03)
```json
{ "elderId": 14, "consentMethod": "PAPER", "scopes": ["POST_PROXY","ACCEPT_PROXY","LOG_CONFIRM","CHECK_IN"],
  "startDate": "2026-11-16", "endDate": "2027-11-15", "consentDate": "2026-11-15", "consentConfirmed": true, "guardianUserId": null }
```
- `startDate` 없으면 오늘, `endDate` 없으면 시작일 + 1년 − 1일, `consentDate` 없으면 오늘.
- `PAPER`, 또는 `GUARDIAN` 인데 `guardianUserId` 가 없을 때: `consentConfirmed:true` 가 있어야 하고 바로 `ACTIVE`.
- `APP`: 본인 앱 계정이 연결돼 있어야 하고 `PENDING` 으로 만들어진다 → 본인에게 알림. 본인이 맡길 일을 고쳐서 동의할 수 있다.
- `GUARDIAN` + `guardianUserId`: `PENDING` → 보호자에게 알림.
- 응답: 위임 상세.

| 코드 | HTTP | 때 |
|---|---|---|
| `CONSENT_REQUIRED` | 400 | 서면·(계정 없는)보호자 동의인데 체크가 없음 |
| `INVALID_METHOD` / `INVALID_SCOPE` / `SCOPES_REQUIRED` | 400 | 값이 정해진 코드가 아님 / 범위가 비었음 |
| `INVALID_PERIOD` / `PERIOD_TOO_LONG` | 400 | 끝나는 날이 시작·오늘보다 앞, 시작이 30일 뒤보다 뒤 / 1년 초과 |
| `INVALID_CONSENT_DATE` | 400 | 동의받은 날이 미래이거나 90일보다 오래됨 |
| `NO_APP_ACCOUNT` | 400 | 앱 동의인데 연결된 본인 계정이 없음 |
| `GUARDIAN_NOT_LINKED` | 400 | 보호자 계정이 본인 계정의 연결된 가족이 아님 |
| `ELDER_ENDED` | 400 | 지원이 종료된 대상 |
| `ALREADY_EXISTS` | 409 | 이미 동의 대기·유효한 위임이 있음 |
| `FORBIDDEN` | 403 | 내 담당 대상이 아님 |

#### `PUT /api/org/delegations/{id}` — 범위·끝나는 날 바꾸기 (서면·보호자 동의만)
```json
{ "scopes": ["POST_PROXY","CHECK_IN"], "endDate": "2027-05-20", "consentDate": "2026-11-16", "consentConfirmed": true }
```
- `scopes`, `endDate` 가운데 바꿀 것만 보낸다. 다시 동의를 받았다는 체크가 꼭 있어야 한다. 끝나는 날은 오늘부터 최대 1년. 만료된 위임도 다시 동의를 받아 이걸로 늘릴 수 있다.
- 바뀌면 변경 기록이 남고, 본인·보호자 계정이 있으면 알림이 간다(프로토타입의 "보호자에게 문자"는 문자 대신 앱 알림 — 연락처를 저장하지 않는다).
- 오류: `APP_OWNED`(409, 앱 동의는 본인만 바꿈), `INVALID_STATE`(409, 회수·거절·대기 중), `CONSENT_REQUIRED`, `NO_CHANGE`, `INVALID_PERIOD`, `PERIOD_TOO_LONG`, `INVALID_SCOPE`.

#### `POST /api/org/delegations/{id}/revoke` — 회수(해지)
- 본문 없음. 동의 대기·유효(만료 전)한 위임만. 응답: 상세(`status:"REVOKED"`). 본인·보호자 계정에 알림. 오류: `INVALID_STATE`(409).

#### `POST /api/org/delegations/{id}/extend-request` — 기간 연장 요청
- 본문 없음. 본인·보호자 **계정에 알림만** 보낸다. 연장은 그 사람이 앱에서 눌러야 된다(1-3). 응답 `{ "ok": true, "id": 3, "message": "연장 동의 요청을 보냈어요" }`.
- 오류: `NO_APP_ACCOUNT`(409, 계정이 없는 분 → 다시 동의를 받아 `PUT` 으로 바꾼다), `INVALID_STATE`(409).

#### `GET /api/org/delegation-requests?status=PENDING|ACCEPTED|REJECTED|CANCELLED|all` — 받은 요청
`status` 없으면 전체. 새 연결(`NEW_LINK`)은 우리 기관 담당자 누구에게나, 범위 변경(`SCOPE_CHANGE`)은 그 대상의 담당자에게만 보인다.
```json
{
  "items": [
    { "id": 5, "kind": "NEW_LINK", "kindLabel": "새 연결", "status": "PENDING",
      "displayName": "김복남 님", "ageGroup": "70대", "dong": "행복동",
      "scopes": ["POST_PROXY","LOG_CONFIRM","PUBLIC_SERVICE","CHECK_IN"], "scopeLabels": ["대신 공고","일지 확인","공공 서비스","안부 확인"],
      "currentScopes": [], "applied": false, "message": "혼자 지내서 담당자님이 챙겨 주시면 좋겠어요.",
      "canReject": true, "acceptLabel": "수락하고 연결", "createdAt": "2026-11-16T09:20:00" },
    { "id": 6, "kind": "SCOPE_CHANGE", "kindLabel": "범위 변경", "status": "PENDING", "displayName": "김영자 님", "elderId": 15, "delegationId": 7,
      "scopes": ["POST_PROXY","LOG_CONFIRM"], "currentScopes": ["POST_PROXY","LOG_CONFIRM"], "applied": true, "canReject": false, "acceptLabel": "확인" }
  ],
  "pendingCount": 2,
  "notice": "앱을 쓰는 분이 '담당 기관 연결'이나 '맡긴 일 바꾸기'를 하면 여기로 와요."
}
```
- `scopes` 는 "바뀐 뒤의 범위 전체"다. 프로토타입의 `대신 수락 끔` 같은 표시는 `currentScopes` 와 비교해 프론트가 만든다.
- `applied:true` = 맡긴 일을 **줄이기만** 한 변경이라 요청과 동시에 이미 반영됐다. 담당자는 `확인`만 누른다(거절 버튼 숨김).
- 새 연결의 `displayName` 은 요청한 사용자의 앱 이름이다(아직 관리 대상이 아니라 별칭이 없다).

#### `POST /api/org/delegation-requests/{id}/answer` — 수락/거절
```json
{ "accept": true, "alias": "김영자", "dong": "희망동" }
{ "accept": false, "reason": "지금은 새 대상을 받기 어려워요" }
```
- 새 연결 수락: `alias`(1~10자, 필수)로 **관리 대상이 새로 등록**되고(나이대·동은 요청한 사람의 프로필 값, `dong` 을 주면 그것), 요청한 범위로 앱 동의 위임이 오늘부터 1년 유효해진다. 담당자는 수락한 사람.
- 범위 변경 수락: 넓히는 변경이면 이때 반영된다. 줄이는 변경은 이미 반영돼 있고 확인 처리만 된다.
- 오류: `INVALID_ALIAS` / `INVALID_DONG` / `PII_NOT_ALLOWED`(400), `ALREADY_APPLIED`(409, 줄이는 변경은 거절할 수 없음), `INVALID_STATE`(409, 이미 처리함·유효한 위임이 없음), `USER_UNAVAILABLE`(409), `FORBIDDEN`(403).

### 1-3. 사용자(본인·보호자) API
담당자 화면에 "받은 요청"과 "동의 대기"가 생기려면 누군가 보내야 하므로 서버만 먼저 만들었다. 화면은 아직 없다(USER 역할만, 아니면 403).

## 2. 기관 공고 3종

기관 이름으로 동네 전체에 올리는 공고. 특정 관리 대상을 위한 요청(대리 요청)과는 다르다.

| `kind` | 이름 | 인원(`capacity`) | 신청하는 사람 | 시간 |
|---|---|---|---|---|
| `VOLUNTEER` | 봉사자 모집 | 1~2명 | 봉사자(신분증 인증·첫 활동 교육 검사) | 참석 확인 때 활동 시간 × 1.0 적립, 차감 없음 |
| `GROUP` | 단체 봉사 | 2~50명 | 봉사자(위와 같음). `teamAllowed` 면 함께 오는 인원(`headCount`)을 적을 수 있음 | 참석이 확인된 신청자 본인에게 활동 시간 × 1.0 적립, 차감 없음 |
| `SERVICE` | 해 드려요 | 1~50명 | 도움이 필요한 사용자(인증 검사 없음) | **적립·차감 없음** |

신청 상태: `APPLIED`(답 기다리는 중) → `JOINED`(확정) / `REJECTED`(거절) → `ATTENDED`(참석·적립) / `ABSENT`(불참) / `SERVED`(방문 완료, 해 드려요). 신청자가 취소하면 `LEFT`(목록에서 빠짐).
묶음(`box`, 프로토타입 `AGRP`): `todo` 처리할 일 = `APPLIED` / `confirmed` 확정 = `JOINED` / `done` 완료 = 나머지.

공고 상태(`state` / `stateLabel`): `OPEN` 모집 중(해 드려요는 "신청 받는 중") / `CLOSED` 마감(마감을 눌렀거나 날짜가 지남) / `DONE` 완료 / `CANCELLED` 취소.

```json

```
- 필수: `kind`, `title`, `category`(앱의 도움 종류), `capacity`, `area`(없으면 담당자 프로필의 동 — 시드 담당자는 동이 비어 있어 꼭 보내야 한다).
- 봉사자 모집·단체 봉사: `date`(오늘 이후), `startHour`, `hours`(30분 단위, 0.5~4시간) 필수.
- 해 드려요: `startHour`+`hours` 또는 `whenText` 가운데 하나. `date` 없으면 오늘 + 30일(신청 마감일). `target`: `ANYONE` 누구나(기본) / `SENIOR65` 65세 이상 / `ALONE` 혼자 사는 분 — **안내 문구일 뿐 신청자를 검사하지 않는다.**
- 봉사자가 하는 두 종류에는 금지 요청 필터(신체 돌봄·의료·금전·위험 작업)를 건다. 해 드려요는 기관 직원이 하는 일이라 걸지 않는다. 모든 종류에서 연락처·상세 주소는 막는다.

| `INVALID_CAPACITY` | 400 | 봉사자 모집 1~2, 단체 봉사 2~50, 해 드려요 1~50 밖 |
| `INVALID_DATE` / `INVALID_TIME` / `INVALID_HOURS` / `WHEN_REQUIRED` | 400 | 날짜·시각 |
| `INVALID_TARGET` / `TOO_LONG` | 400 | |

| `PII_NOT_ALLOWED` | 400 | 연락처·상세 주소 |

#### `GET /api/org/notices/{id}` — 공고 상세 + 신청자
목록 한 장 + `applications`(아래 신청 모양, `notice` 칸 없음). 우리 기관 공고가 아니면 403.

#### `POST /api/org/notices/{id}/close` · `/reopen` — 신청 마감 · 다시 열기
- 마감은 **새 신청만** 막는다. 확정된 사람의 활동·방문과 답하지 않은 신청은 그대로다. 오류: `ALREADY_CLOSED`(409), `INVALID_STATE`(409).

#### `DELETE /api/org/notices/{id}` — 공고 내리기
- `status:"CANCELLED"`. 신청·확정한 사람 모두에게 알림.

#### `POST /api/org/notices/{id}/complete` — 참석 확인·완료 (봉사자 모집·단체 봉사)
```json
{ "attended": [101, 102] }
```
- 활동하는 날부터. 확정된 사람 가운데 `attended` 에 있는 사용자는 `ATTENDED` + 통장에 `hours × 1.0` 적립, 없는 사람은 `ABSENT`. 답하지 않은 신청은 거절로 닫힌다. 응답: 상세 + `result: { attended, absent, earnedEach, totalEarned }`.
- 프로토타입은 "당일 기관에서 QR로 시작·종료"라고 적혀 있지만, 단체 봉사와 같은 방식(담당자가 참석 확인)으로 했다(7장).
- 오류: `TOO_EARLY`(409), `ATTENDED_REQUIRED` / `NOT_PARTICIPANT`(400), `INVALID_KIND`(400, 해 드려요), `INVALID_STATE`(409).

#### `POST /api/org/notice-applications/{id}/approve` — 수락(확정)
- 봉사자 모집·단체 봉사: 본문 없음. 해 드려요: `{ "visitDate": "2026-11-17", "visitStartHour": 14, "visitHours": 1 }`(`visitHours` 없으면 1시간).
- 확정 인원 + 이 신청의 인원이 정원을 넘으면 `FULL`(409). 신청자에게 알림. 응답: 신청 한 건.
- 오류: `VISIT_REQUIRED` / `INVALID_DATE` / `INVALID_TIME`(400), `ID_NOT_VERIFIED` / `EDU_REQUIRED`(400, 그 사이 봉사 자격이 없어짐), `FULL`(409), `INVALID_STATE`(409), `USER_UNAVAILABLE`(409).

#### `POST /api/org/notice-applications/{id}/reject` — 거절
- `{ "reason": "이번에는 인원이 찼어요" }`(선택, 200자, 연락처 금지). 신청자에게 알림.

#### `POST /api/org/notice-applications/{id}/served` — 방문 완료 (해 드려요)
- 확정된 신청만, 방문하는 날부터. `SERVED` 로 바뀔 뿐 통장에는 아무것도 기록되지 않는다. 오류: `INVALID_KIND`(400), `INVALID_STATE` / `TOO_EARLY`(409).

### 2-3. 기존 단체 봉사 API 와의 관계
- 기관 공고는 `GET /api/group-posts`, `GET /api/group-posts/mine` 에 **나오지 않는다**(지금 화면이 모르는 상태값 `APPLIED` 가 보이지 않게).
- `POST /api/group-posts/{id}/join` 을 기관 공고에 부르면 409 `CANNOT_JOIN`("기관 공고는 신청한 뒤 담당자가 확정해요").
- 확정된 봉사자 모집·단체 봉사는 `GET /api/group-posts/schedule`(플래너 달력)에 지금처럼 `[단체] 제목` 으로 나오고, 참석이 확인되면 확인서·리포트·통계에 단체 봉사와 같이 세어진다. 해 드려요는 나오지 않는다.
- 기관 행사(`/api/org/events`, `org_events`)는 건드리지 않았다.

- 누가 나오나: 내 관리 대상(지원 중)의 요청에 걸린 봉사자 가운데 ① 지금 응답 대기·확정·진행 중인 요청이 있거나 ② 최근 60일 안에 활동을 마쳤거나 ③ 내 대상의 단골(같은 대상과 완료 3회 이상)인 사람. 새로 저장하는 값은 없다.
- 상태(먼저 맞는 것 하나) — 정렬도 이 순서, 같으면 가까운 일정 → 완료 횟수 많은 순.

| `state` | `stateLabel` | 기준 |
|---|---|---|
| `ACTIVE_NOW` | 활동 중 | 요청 상태 `IN_PROGRESS`(시작을 찍고 아직 안 끝남) |
| `TODAY` | 오늘 예정 | 오늘 날짜의 `CONFIRMED` |
| `SCHEDULED` | 예정 | 내일 이후의 `CONFIRMED` |
| `PENDING` | 응답 대기 | 오늘 이후의 `SENT`·`VOL_ACCEPTED` |
| `IDLE` | 대기 | 그 밖 |

- `sub`(둘째 줄): 일정이 있으면 `오늘 14:30 별칭 님` / `11/18(수) 10:00 별칭 님`, 없으면 `단골 n명`, 그것도 없으면 `최근 활동 11/6(금)`.
- `regularCount` = 이 봉사자를 단골로 둔 **내** 관리 대상 수. `counts.regulars` = 단골이 한 명이라도 있는 봉사자 수.
- `limit` 을 줘도 `counts` 는 전체 기준이다.
- 대상 이름은 별칭이다. 남의 관리 대상·다른 기관 자료는 섞이지 않는다.

## 4. AI 도우미

#### `GET /api/org/assistant` — 패널 열 때
`{ "name": "담당자 도우미", "suggestions": ["이번 주 빈칸 정리해줘", "먼저 안부 물어볼 분 알려줘", …], "notice": "…", "maxLength": 300 }` (AI를 부르지 않는다)

#### `POST /api/org/assistant`
요청 `{ "question": "이번 주 빈칸 정리해줘", "screen": "O-SCHED-01" }` (`screen` 은 선택 — 지금은 되돌려주기만 한다)
```json
{
  "question": "이번 주 빈칸 정리해줘", "screen": "O-SCHED-01", "executed": false,
  "intent": "GAPS",
  "text": "이번 주 빈칸이 3개 있어요. 편성표에서 칸을 누르면 봉사자 추천을 보고 직접 요청할 수 있어요.",
  "card": { "title": "빈칸 3개", "link": "/o/schedule", "linkLabel": "편성표 열기",
            "rows": [ { "label": "이순례 님 · 11/18(수)", "value": "동행 · 지난 4주 중 3주 수요일에 동행 방문이 있었어요", "link": "/o/schedule?elder=11" } ] },
  "facts": { "gaps": 3, "fixed": 9, "weekStart": "2026-11-16" },
  "source": "rule",
  "notice": "숫자와 목록은 시스템이 계산했고, AI는 문장만 다듬어요. 수락·등록·위임은 화면에서 직접 눌러야 바뀌어요.",
  "suggestions": ["이번 주 빈칸 정리해줘", "…"]
}
```
- `text` = 말풍선, `card` = 그 아래 카드(`title` + 오른쪽 버튼 `linkLabel`→`link` + `rows`). `card` 는 null 일 수 있다.
- `source`: `rule`(규칙 문장) 또는 `ai`(AI가 문장을 다듬음, 이때 `provider` 가 붙는다). **카드·숫자·링크는 어느 쪽이든 서버가 실제 자료로 만든 것**이다.
- `executed` 는 늘 false — 공고를 올리거나 수락하지 않는다.
- 오류: `QUESTION_REQUIRED` / `TOO_LONG`(400, 300자), `FORBIDDEN`(403, ORG 아님).

**의도(`intent`)와 답** — 규칙 낱말은 프로토타입 `answer(q)` 의 묶음에 새 화면 낱말을 더했다.

| `intent` | 낱말(규칙) | 자료 | 카드 링크 |
|---|---|---|---|
| `GAPS` | 빈칸·편성 | 이번 주 편성표의 빈칸(`/api/org/schedule` 와 같은 계산) | `/o/schedule` |
| `CHECK_FIRST` | 안부·리포트·변화 | 변화 리포트의 "먼저 확인" 순서(최근 30일 기록, 규칙 계산만) | `/o/report` |
| `WEATHER` | 한파·특보·폭염·대설·호우·태풍·날씨 | 내 담당 지역에 진행 중인 특보, 대상 수, 기간 안 활동 수, 할 일 목록 | `/o/weather` |
| `DELEGATION` | 위임·동의·만료·맡긴 일 | 위임 개수(유효·만료 임박·만료·없음·받은 요청)와 확인할 대상 | `/o/delegations` |
| `APPLICATIONS` | 신청·기관 공고·모집·해 드려요 | 답할 신청 수·확정 수와 신청 목록 | `/o/notices?tab=apps` |
| `VOLUNTEERS` | 봉사자·단골 | 3장 봉사자 현황 | `/o/home` |
| `TODO` | 처리할·할 일·오늘·대기·수락·일지 | 최종 수락·제안, 일지 확인, 시간 조정, 기관 공고 신청, 위임 요청 건수 | `/o/reqs` |
| `DRAFT` | 공고·동행·올려·요청·장보기·말동무·병원 | 질문 속 별칭으로 **내** 관리 대상을 찾아 대리 요청 초안(대상·도움 종류·날짜·주의사항·단골)을 보여 줌 | `/write/need?elderId=…&cat=…&date=…` |
| `HELP` | 그 밖 | 무엇을 도울 수 있는지 안내 | 없음 |
| `NO_DIAGNOSIS` | 치매·우울증·진단·증상… | "건강 상태를 판단하는 말은 하지 않아요" + 리포트 링크 | `/o/report` |
| `EMERGENCY` | 응급 낱말(기존 `VoiceSafety`) | 기존 응급 안내 문장 | 없음 |

- `DRAFT` 는 **초안을 보여 줄 뿐 저장하지 않는다.** `card.draft = { elderId, category, date }` 를 쓰기 화면에 미리 채우면 된다(`category`·`date` 는 질문에서 못 읽으면 null). 별칭이 내 관리 대상에 없으면 대상을 고르라는 카드가 나온다(남의 대상 이름은 나오지 않는다).
- "올려줘·수락해줘·승인해줘"처럼 대신 해 달라는 말에는 답 끝에 `수락·등록 같은 결정은 제가 대신하지 않아요. 화면에서 확인하고 직접 눌러 주세요.` 가 붙는다(이 문장은 AI가 다듬지 않는다).
- AI를 쓰는 곳은 두 군데뿐이다(`AiClient` → `LlmJson` 경유, 키가 없으면 규칙): ① 규칙으로 못 나눈 질문의 의도 고르기 ② `text` 다듬기. 다듬은 문장은 **근거(규칙 문장 + `facts`)에 없는 숫자가 있거나, 진단하는 말·연락처가 있으면 버리고** 규칙 문장을 쓴다. 질문 속 연락처·주소는 지우고 보낸다.
- 대화 기록은 서버에 저장하지 않는다. 한 번에 한 질문만 본다(앞 대화를 기억하지 않음).

## 6. 기존 것을 넓혀 쓴 곳과 판단 근거

| 프로토타입 | 한 일 | 근거 |
|---|---|---|
| 기관 공고 "단체 봉사" | 기존 `group_posts`(모집형 RECRUIT) 그대로 + `org_kind=GROUP` | 올리는 쪽(기관)·인원·참석 확인·개인별 적립이 같다. 다른 점은 "신청 → 담당자 수락"뿐이라 신청 상태값만 더했다 |
| 기관 공고 "봉사자 모집" | 같은 표 + `org_kind=VOLUNTEER`(1~2명) | 단체 봉사와 인원 수만 다르다. 1:1 공고(`posts`)는 받는 사람(관리 대상·사용자)이 있어야 하고 받는 쪽 시간이 차감되는 흐름이라 맞지 않는다 |
| 기관 공고 "해 드려요" | 같은 표 + `kind=SERVICE`, 방문 일정 칸 | 공고·정원·신청·수락 구조가 같다. 적립만 없어서 완료를 `SERVED` 로 따로 두고 `GroupService.complete` 에서 막았다. 표를 따로 만들면 목록·신청·알림을 두 벌 만들어야 한다 |
| 신청·수락·거절 | 기존 `group_participants` 에 상태값·칸 추가 | 한 사람 한 줄, 공고에 딸린 구조가 같다 |
| 적립 | 기존 `GroupService.complete` 를 그대로 부름 | 적립 계산(시간 × 1.0)과 통장 기록을 한 곳에 둔다 |
| 기관 행사 | 건드리지 않음 | 프로토타입도 "시간과 상관없는 안내라 기관 행사에서 따로"라고 나눈다(O-POST-06). 행사 신청(`event_applications`)은 수락 단계가 없는 다른 흐름 |
| 봉사 자격 검사 | 기존 `VolunteerGate` | 1:1·단체와 같은 기준 |
| 봉사자 현황 | 기존 `requests` 만 읽음 | 새로 저장할 값이 없다 |
| AI 도우미 자료 | 기존 `CareScheduleService.week`, `ElderChangeService.report`, `WeatherAlertService.forManager` + 새 서비스 3개 | 화면과 같은 계산을 다시 써서 숫자가 화면과 어긋나지 않게 |
| 위임 "위임으로 한 일" | 기존 대리 공고·요청에서 읽음 | 따로 쌓으면 같은 사실을 두 번 저장하게 된다 |

기존 코드에서 바꾼 곳은 `domain/GroupPost.java`, `domain/GroupParticipant.java`(칸 추가)와 `service/GroupService.java` 7곳이다: 참여자 셈에서 `APPLIED`·`REJECTED` 제외, 기관 공고에는 선착순 참여 막기, 해 드려요는 적립 완료 막기, 카드에 `orgKind`·이름, 목록·내 목록에서 기관 공고 빼기, 플래너 일정에서 해 드려요 빼기. 예전 단체 봉사(`org_kind` 없음)의 동작은 그대로다(기존 `GroupTest`·`GroupJoinLockTest` 통과).

## 7. 프로토타입과 다르게 한 곳

| 프로토타입 | 한 것 | 이유 |
|---|---|---|
| 관리 대상 연락처 카드(전화·주소·가족 이름·전화), 📞 전화 걸기 | 만들지 않음 | 서비스 규칙: 실명·전화·주소·가족 연락처를 저장하지 않는다 |
| 서면 동의 "서명한 동의서 사진·PDF 올리기" | 파일을 받지 않고 `consentConfirmed` 체크 + 날짜만 | 서류 사본·서명을 저장하지 않는다 |
| 보호자 동의 "등록된 가족 연락처로 동의 링크 문자" | 가족 연결된 **앱 계정**이 있으면 그 계정에 알림 → 앱에서 동의. 없으면 담당자가 동의를 받았다고 체크 | 가족 연락처를 저장하지 않는다 |
| 범위를 바꾸면 "보호자에게 문자" | 본인·보호자 계정이 있으면 앱 알림 | 위와 같음 |
| 동의 방법 이름 "서면 동의서", "보호자 동의 (문자)" | `서면 동의`, `보호자 동의` | 서류·문자를 다루지 않으므로 |
| 받은 요청 "범위 변경"에 거절 버튼 | 맡긴 일을 **줄이는** 변경은 요청 즉시 반영, 담당자는 확인만(거절 불가). 넓히는 변경은 수락해야 반영 | 맡긴 일을 거두는 것은 본인 뜻이라 담당자가 막을 수 없어야 한다 |
| 새 연결 수락 → "관리 대상에 추가돼요" | 수락할 때 담당자가 **별칭**을 정해야 함 | 관리 대상은 별칭으로만 기록한다(앱 이름을 그대로 옮기지 않음) |
| 위임 목록의 나이(`82세`) | 나이대(`80대`) | 숫자 나이를 저장하지 않는다 |
| "위임으로 한 일"의 처리한 담당자 이름 | 대리 공고만 이름이 나오고 일정 확정·일지 확인은 이름 없음 | 그 두 가지는 누른 사람을 저장하지 않는다(지어내지 않음) |
| "담당자 간 위임" 탭(기간 동안 대리·이관) | 만들지 않음 | 이번 범위(대상·보호자 → 담당자 위임)가 아니다. 완전 이관은 기존 이관 기능이 있고, "기간 동안 대리"는 권한 검사 전체에 걸리는 일이라 따로 결정이 필요 |
| 기관 공고 "당일 QR로 시작·종료" | 담당자가 참석 확인(단체 봉사와 같음) | 30초 QR 은 1:1 요청에만 있다. 넓혀 쓰는 단체 봉사 흐름을 그대로 따랐다 |
| 봉사자 모집 "반복: 매주·격주", 날짜 `매주 목` | 한 번짜리만 | 정기 요청(`recurring_posts`)은 1:1 공고 전용이다 |
| 해 드려요 "신청 방법: 전화 신청도 받기" | 앱 신청만 | 전화 신청을 기록할 곳·방법이 정해지지 않았다 |
| 해 드려요 "노출 범위 1km·3km·구 전체" | 동(`area`)으로만 거름 | 앱에 실제 거리 자료가 없다 |
| 해 드려요 "받을 수 있는 인원: 이번 달 6명" | 공고 한 건의 정원 | 달마다 다시 채우는 규칙이 없다 |
| 해 드려요 대상(65세 이상·혼자 사는 분) | 안내 문구로만 | 가구 형태를 저장하지 않고, 나이대로 신청을 막을지는 결정 전 |
| 완료된 봉사 신청 "봉사자 적립 1.5시간" | 실제 `earned` 값(활동 시간 × 1.0) | 가중치는 1.0·1.2만, 단체·기관 공고는 1.0 |

## 8. 프론트에서 필요한 일

1. **메뉴·경로**: `권한 위임`(O-DLG-01) 메뉴, `기관 공고`(O-POST-05) 메뉴를 새 화면으로. 지금 `기관 공고 > 단체 봉사 공고` 가 가리키는 `/board?tab=group&kind=mine` 에는 기관 공고가 나오지 않는다. 서버가 알림·카드에 넣는 경로는 `/o/delegations`(`?tab=requests`, `?elder=`), `/o/notices`(`?tab=apps&app=`), `/my/delegations`, `/org-notices/:id` — 다르게 정하면 `DelegationService`·`OrgNoticeService`·`OrgAssistantService` 의 링크 상수를 맞춘다.
2. **권한 위임 화면**: 목록(1-2) + 오른쪽 상세(범위 5줄: `editableByManager` 면 스위치 → 저장 때 "다시 동의 받음" 체크와 함께 `PUT`, 아니면 켜짐/꺼짐 글자) + `기간 연장 요청`(`canAskExtend`) · `해지`(`canRevoke`) + 변경 기록(`history`) + 위임으로 한 일(`acts`). 탭 `위임 목록 | 받은 요청 n`(`counts.requests`). "담당자 간 위임" 탭은 없음.
3. **받은 요청 카드**: `kindLabel`, 범위 태그(`scopeLabels`, 범위 변경은 `currentScopes` 와 비교), `message`, 버튼 `acceptLabel` / 거절(`canReject`). 새 연결 수락 때 **별칭 입력 창**.
4. **새 위임 등록 패널**(O-DLG-03): 대상 칩 → `GET /api/org/elders/{id}/delegation` 로 `canCreate`·`appLinked`·`guardianCandidates` 확인 → 동의 방법 3가지(파일 올리기 칸 없음, 서면·계정 없는 보호자는 체크박스) → 맡길 일 → 시작·끝(최대 1년).
5. **관리 대상 상세의 "권한 위임" 카드**: 같은 API. 연락처·주소·가족 카드는 만들지 않는다.
6. **기관 공고 화면**: 탭(전체·3종, `counts`) + 카드 격자 + `신청 n건 보기`(`pendingApplications`) + `+ 공고 올리기`(종류 고르기 = `kinds`) + 종류별 쓰기 패널(2-1 표의 칸) + `마감`(`canClose`) · 참석 확인(`canComplete` → 참석자 고르는 창, 단체 봉사 화면의 것을 다시 쓸 수 있음).
7. **요청 관리의 "기관 공고 신청" 탭**(O-POST-09): `처리할 일 | 확정 | 완료`(`counts`) + 종류 칩 + 목록·상세 두 칸. 수락(해 드려요는 방문 날짜·시각 입력) · 거절(사유) · 방문 완료(`canServe`).
8. **홈**: 숫자 칩 "새 신청"(`notice-applications` 의 `counts.todo`), "새로 온 요청"의 "기관 공고 신청" 줄, 오른쪽 "봉사자 현황" 4줄(`/api/org/volunteers?limit=4`, 상태 배지 `stateLabel`, 둘째 줄 `sub`), 아래 "기관 공고 진행" 4장(`/api/org/notices`). 지금 그 자리에 있는 "바로 하기"·"이번 주 브리핑"을 어디로 옮길지는 화면 쪽 결정.
9. **AI 도우미 패널**: 떠 있는 버튼 + 패널(열 때 `GET`, 물을 때 `POST`). 말풍선 `text`, 카드(`card.title` · `linkLabel` 버튼 · `rows`), 예시 칩 `suggestions`, 아래 작은 글 `notice`, `source==='ai'` 표시. 대화 목록은 프론트 메모리에만. `DRAFT` 카드는 `card.link` 로 쓰기 화면에 가서 `elderId`·`cat`·`date` 를 미리 채운다(지금 `/write/need` 가 이 쿼리를 읽는지 확인 필요).
10. **사용자 쪽(다음 차수)**: 담당 기관 연결·맡긴 일 바꾸기·동의·회수·연장 화면(1-3), 기관 공고 보기·신청·내 신청(2-2). 이것이 없으면 실제 데이터는 시드와 담당자 등록분만 생긴다.
11. **알림 종류** `DELEGATION`, `ORG_NOTICE` 가 새로 온다(끌 수 없는 종류). 알림 화면에 아이콘·이동 경로를 더한다.

**시드(데모 `org1`)**: 위임 3건(서면·보호자·서면 만료 임박) + 위임 없는 대상 1명 + 받은 요청 1건(새 연결), 기관 공고 3건(봉사자 모집·단체 봉사·해 드려요)과 신청 6건. 위임·기관 공고가 하나도 없을 때만 들어간다(`Org1116Seeder`).

## 9. 확인 못 한 것 · 결정이 필요한 것

- **위임 범위를 기존 동작에 걸지 않았다.** 대리 공고 올리기·대신 수락·일지 확인·공공 서비스 연계는 지금처럼 위임이 없어도 된다. 걸면 위임 기록이 없는 기존 관리 대상의 모든 대리 처리가 막힌다. `DelegationService.allows(elderId, scope)` 는 준비돼 있다 — 언제부터, 기존 대상을 어떻게 옮길지 결정이 필요하다.
- `db/schema.sql`, `db/README.md`, `docs/design/contract.md` 는 고치지 않았다(이번 범위 밖). MySQL 로 띄우는 환경이면 5장의 표·칸을 스키마 파일에 더해야 한다.
- 서버를 띄워 화면과 맞춰 보지 않았다(서버 실행 금지). 통합 테스트(MockMvc, 메모리 DB)로만 확인했다. 실제 AI 호출은 하지 않았고, AI 경로는 가짜 응답(mock)으로만 확인했다.
- 시드는 `SeederSmokeTest` 가 도는 것까지만 확인했다(시드 내용을 따로 검사하는 테스트는 없다). 이미 데이터가 있는 `./data` DB 에 칸이 자동으로 더해지는지는 띄워 보지 않았다.
- 위임 만료 알림(끝나기 30일 전 자동 알림)은 만들지 않았다. 지금은 목록의 "만료 임박" 표시와 담당자의 연장 요청 버튼뿐이다.
- AI 도우미 호출 횟수 제한이 없다. 운영 키로 켤 때는 담당자별 하루 상한을 정해야 한다.
- 새 연결 요청의 `displayName` 은 요청한 사용자의 앱 이름이다. 관리 대상이 되기 전이라 별칭이 없어서인데, 이 자리도 가려야 하는지 확인이 필요하다.
- 해 드려요 신청 메시지에는 건강 이야기가 들어올 수 있다(예: 프로토타입의 "혼자 씻기 힘들어해요"). 연락처·주소만 막고 그대로 저장한다 — 보관 기간·열람 범위(지금은 그 기관 담당자만) 확인이 필요하다.
